# README 内容适配模型

## 用途

结构与适用性按 `output-contract.md` 决策；本文件提供不同类型的内容检查项。

## 内容组织原则

- 开头先说明项目定位、目标读者和解决的问题。
- 能力说明应连接“场景或问题—系统能力—使用入口—产出”，不能只列技术名词。
- 至少写一条完整使用路径，让读者知道如何从入口得到结果。
- 架构内容说明主要运行单元、依赖方向和数据流；简单项目用短表，复杂关系才使用 Mermaid。
- 目录结构只列影响代码定位、配置、测试、文档和构建产物的路径。
- 技术栈、版本要求、端口和命令来自清单文件、脚本、配置和实际验证。
- 常用工作流按使用场景组织，不把安装、测试、构建、部署和排障命令混成一段。
- 开发契约只摘要不可破坏的不变量，详细规则链接 `AGENTS.md` 或其它权威文档。
- README 是项目入口，不复制完整架构、API、需求、部署或 AI 协作说明。

## 内容深度

### 小型脚本、单包或简单库

核心章节保持完整，内容可以简短。架构、配置、部署等条件章节没有事实触发时省略。重点确保最小运行示例、输入输出、验证命令和适用边界清楚。

### 中型应用或服务

除核心章节外，通常需要架构与代码结构、配置与环境变量；存在数据库或部署材料时增加数据准备、部署运维。能力说明应覆盖主要入口和一条端到端使用链路。

### 复杂全栈、数据系统或 Monorepo

在适用位置中补充运行单元、workspace 或服务关系、数据流、构建顺序、生命周期、外部依赖和故障排查。图表只表达文本难以说明的三方以上关系，不重复表格内容。

## 表达方式

- 表格用于能力、模块、命令、配置和文档入口的横向映射。
- Mermaid 用于组件关系、请求路径、任务流或数据流；简单线性步骤使用列表。
- 示例应能直接对应当前项目入口，不使用来源不明的样例模块、端口、账号或数据口径。
- 详细说明放在对应相应主题下的三级标题中，避免重复。
