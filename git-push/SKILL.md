# Git 提交与推送

## 职责与边界

负责确定提交范围、暂存、提交及已授权的推送；提交消息必须由 [git-commit-message-authoring](../git-commit-message-authoring/SKILL.md) 生成，不在本技能维护消息模板。本文维护 Git 写入顺序、范围保护及调用模式；项目规范维护仓库检查和验证要求。

## 输入与前置条件

核对目标仓库、分支、上游、工作区及已有暂存内容。用户指定文件时只处理指定范围；未指定时根据会话与 diff 选择可可靠归属本任务的改动。保护无关改动及用户原有暂存内容，不把它们混入本次提交；无法安全隔离范围时停止并报告原因。

| 调用方式 | 执行规则 |
| --- | --- |
| 普通请求 | “提交”“推送”“提交并推送”等请求：自行核定范围、消息和暂存结果，不逐步询问。只要求提交就不推送；已要求推送则提交成功后直接推送。无法确定范围时报告具体阻塞。 |
| 显式调用 | 仅 `$git-push` 或明确要求使用本技能，执行下方确认节点。讨论、审查或修改技能不属于调用。 |

### 显式调用的确认节点

仅此模式执行下列节点；确认前读取 [全局协作规则“需要先确认时”](~/ai-agent-config/config/force/collaboration-rule.md#需要先确认时)，统一使用其工具优先、受限降级及授权复用机制。每次展示对应范围与依据，已有精确覆盖对应节点的确认直接复用。

| 节点 | 需核定内容 |
| --- | --- |
| 范围 | 展示文件及用途；未指定时提供全部改动、推荐任务范围及自定义选择。多个独立需求让用户选择缩小范围或合并为一次提交。 |
| 消息 | 调用消息技能后展示文案、对应范围和主要依据，确认后才能暂存。 |
| 暂存 | 展示实际 staged 清单，选择继续本地提交、直接提交并推送或调整。选择直接提交并推送时同时取得两项授权，不再重复确认。 |
| 执行方式 | 暂存节点尚未确定提交方式时，再选择仅提交或提交并推送。若此时选择推送，提交后展示提交摘要并完成最终推送确认；此前已有精确覆盖的直接推送授权则复用。 |

## 执行流程

1. **确定范围**：读取 `git status`、未暂存及暂存差异，按调用方式核定文件和多需求处理。范围确定后不额外加入文件。
2. **生成消息**：读取并调用消息技能，传入文件范围、改动摘要、多需求处理决定、用户明确提供的来源与文档、实际验证结果。属于内部调用，不让消息技能重复确认；依赖缺失或不可读时停止提交。
3. **暂存与核对**：完成当前模式适用节点后，按确定路径执行 `git add -- <paths>`。运行 `git diff --cached --name-status` 及必要差异检查，确保内容与范围一致。用户未明确选择全部改动时不使用 `git add -A` 或 `git add .`。
4. **提交**：锁定实际暂存清单及内容；提交前重新核对，发生变化时暂停重新审阅，显式模式取得变更范围确认。锁定后不再添加文件。一次流程生成一条消息并执行一次 commit，不擅自拆分多个提交。
5. **推送**：commit 成功且本次模式所需推送授权成立后，核对待推送提交和目标，执行正常 push。提交失败不推送；推送失败保留本地提交并报告，不擅自强推、重写共享历史或切换远端。

## 核心约束

- 构建产物、依赖缓存、锁文件、配置、其他模块、IDE 文件、日志和临时文件不得作为附带改动纳入；用户明确指定的任务文件按其范围核对，敏感内容仍不得泄露。
- 不通过重置、丢弃或擅自 stash 来清理用户改动；不能用只核对文件名代替暂存内容核对。
- 内部调用消息技能不产生新确认流程；普通提交请求不进入上述显式确认节点。
- 已有有效授权持续生效；只提交不等于授权推送，提交成功不等于推送成功。

## 产出边界与交付

交付提交标识、实际范围、提交及推送结果、失败位置和保留状态。没有新增改动时核对已有待推送提交，按用户的推送授权处理，不创建空提交。

## 验证与完成标准

提交前核对范围、内容与授权，提交后核对实际 commit；推送后核对命令结果与远端分支状态。失败明确停在哪一步，保护原工作区和暂存内容，不将部分成功报告为全部完成。
