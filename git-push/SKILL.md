# Git Push

请按以下流程执行 Git 提交与推送操作。

## 0. 交互方式强制约束

**所有需要用户确认或选择的步骤，必须使用 `AskUserQuestion` 工具弹出选项窗口，禁止使用纯文本提问让用户手动输入回复。**

适用范围

- 凡是流程中提到“向用户确认”“让用户选择”“等待用户确认”的所有节点

实现要求：

1. 每个确认节点都必须显式调用 `AskUserQuestion`，给出所涉及的明确选项。
2. 必要的上下文（文件清单、commit 摘要、push 范围等每个要确认的节点）在调用前先用普通文本展示，再用 `AskUserQuestion` 让用户点选。
3. 即使是简单的“是否继续”，也必须用弹窗（至少 2 个选项：继续 / 取消）。

违反此约束等同于违反“安全红线”，必须立即中止并改用 `AskUserQuestion` 重新询问。

## 1. 确定提交文件范围

### 1.1 用户主动指定文件
- 如果用户在请求中明确提到了要提交哪些文件（例如“提交 detail.vue”“只提交前端文件”“@ 对应文件”），则直接选择用户指定的文件。
- 严禁自作主张添加用户未提及的其他文件，即使用户提到的文件很少。

### 1.2 用户未指定时提供选项
- 如果用户没有明确指定要提交的文件，则：
  1. 先运行 `git status --short` 查看当前有改动的文件。
  2. 再结合当前会话中实际编辑/修改过的文件，生成推荐列表并简要说明推荐原因。
  3. 向用户提供以下三个选项，让用户选择：
     ```
     请选择要提交的文件范围：
     1. 所有改动文件（共 X 个文件）
        - 列出所有改动文件（如某目录文件很多，则写“目录 + 文件数量”）
     2. 智能建议（推荐 X 个文件）
        - 业务说明
        - 文件 1（具体业务说明）
        - 文件 2（具体业务说明）
     3. 其他：用户自己说明要提交的文件
     ```
  4. 根据用户的选择确定要提交的文件清单。

### 1.3 文件范围确认
- 在执行任何 `git add` 之前，必须先向用户列出准备提交的文件清单，例如：
  ```
  准备提交以下文件：
  - src/views/riskManagement/mechanismEffectScore/detail.vue（前端详情页添加返回按钮）
  - src/views/riskManagement/mechanismEffectScore/index.vue（前端列表页修复）
  ```
- 用户确认文件范围后，后续只能按该范围执行，禁止额外添加文件。

## 2. 生成提交信息并先确认

在执行 `git add` 之前，先根据已确认的文件范围和改动内容生成提交信息，并先让用户确认提交文案。

生成提交信息前，应根据已确认文件读取必要 diff 摘要，理解改动类型、业务主体和改动目的；不要只根据文件名机械拼接提交信息。

### 提交消息模板

```text
[项目简写].操作类型_功能描述：业务主体 - 需求来源 - 具体内容
```

### 格式说明

| 组成部分 | 说明 | 示例 |
|---------|------|------|
| 项目简写 | 从当前目录名推断或用户指定 | `xhd`、`wf` |
| 操作类型 | 新增 \| 更新 \| 修复 \| 删除 \| 重构 | `新增`、`更新`、`修复` |
| 功能描述 | 简洁的功能说明 | `用户管理接口`、`加密工具类` |
| 业务主体 | 主要文件/接口/服务/代码 | `UserController`、`SecurityUtils` |
| 需求来源 | 有需求编号则填写，无则用“自研” | `101`、`自研` |
| 具体内容 | 对功能和需求的简化概括 | `加入分页查询、基础 CRUD 方法` |

### 操作类型判定规则

- 新增：新文件、新接口、新功能、新模块
- 更新：现有功能增强、逻辑调整、配置变更、文档补充
- 修复：Bug 修复、问题处理、逻辑纠正
- 删除：移除文件、废弃接口、清理代码
- 重构：代码结构重组，原则上不改变业务行为

### 示例

```text
xhd.新增_用户管理接口：UserController-101-加入分页查询、基础 CRUD 方法
xhd.新增_加密工具类：SecurityUtils-自研-加入对称加密相关方法
wf.更新_AJAX 示例：axios.html-fetch.html-原生 AJAX 请求封装
```

### 多文件提交处理

如果涉及多个文件或功能，可以分行书写：

```text
[项目简写].功能 1：需求来源 1-内容 1
[项目简写].功能 2：需求来源 2-内容 2
```

### 提交信息确认

- 向用户展示生成的提交信息，并同时展示提交信息对应的文件范围和主要改动依据。
- 若用户认为文案不合适，先调整提交信息，再进入 `git add`。
- 在用户确认提交信息前，不执行 `git add`、`git commit` 或 `git push`。

## 3. 按确认范围执行 git add

### 3.1 执行原则
- 根据用户确认的文件清单执行 `git add <文件路径>`。
- 只能添加用户明确确认的文件。
- 严禁使用 `git add -A` 或 `git add .` 等批量添加命令，除非用户明确选择“所有改动文件”。

### 3.2 默认禁止附带添加的文件

除非用户明确提到，严禁添加以下类型文件：

- 前端构建产物（`static/`、`dist/`、`build/`）
- 包管理器缓存（`node_modules/`、`.pnpm-store/`、锁文件等）
- 配置文件（`pom.xml`、`bootstrap*.yml`、`.env*`、`application*.yml` 等）
- 其他业务模块文件
- IDE/编辑器配置（`.idea/`、`.vscode/`、`*.iml`）
- 日志/临时文件（`*.log`、`tmp/`、`*.tmp`）

### 3.3 staged 最终确认

- 执行 `git add` 后，必须运行能清晰展示 staged 文件的命令，并向用户展示结果。
- 优先使用：
  - `git diff --cached --name-status`
  - 必要时补充 `git status --short`

- 向用户确认：
  ```
  已 staged 的文件如下（请确认只有你同意提交的文件）：
  <staged 文件清单>

  请确认：
  1. 文件清单正确，继续 commit
  2. 文件清单有误，需要修正
  ```

- 只有用户确认 staged 文件清单正确后，才能继续执行 `git commit`。

## 4. 确认提交方式并执行

### 4.1 提交方式确认

在 staged 文件和提交信息都确认后，再向用户确认执行方式：

```text
提交信息：
<commit message>

请确认提交方式：
1. 仅提交（执行 git commit，不推送）
2. 提交并推送（执行 git commit → git push）
3. 其他：用户自己说明
```

### 4.2 执行逻辑

- 如果用户选择 1，则执行 `git commit` 后停止。
- 如果用户选择 2，则执行 `git commit`，成功后再执行 `git push`。
- 如果用户选择 3，则按用户说明执行。

### 4.3 push 前确认

- 如果用户选择“提交并推送”，则在 `git commit` 成功后、`git push` 之前，必须再次做一次最终确认：
  ```
  即将推送以下 commit：
  <git log -1 --stat>

  确认要执行 git push 吗？(yes/no)
  ```
- 只有用户明确确认后，才能执行 `git push`。

## 5. 执行顺序（固定）

严格按以下顺序执行，不要打乱；**所有"确认"环节必须使用 `AskUserQuestion` 弹窗，禁止纯文本提问**：

1. 确定文件范围
2. 展示并通过 `AskUserQuestion` 确认文件范围
3. 读取确认范围内的 diff 摘要，生成提交信息并通过 `AskUserQuestion` 确认
4. 按确认范围执行 `git add`
5. 展示 staged 文件清单并通过 `AskUserQuestion` 确认
6. 通过 `AskUserQuestion` 确认提交方式
7. 执行 `git commit`
8. 若用户选择 push，则通过 `AskUserQuestion` 再次确认后执行 `git push`

## 6. 注意事项

- 提交信息要简洁清晰，符合用户项目的模板规范。
- 项目简写可从当前目录名推断，也可询问用户确认。
- 需求来源如果用户没有提供，则使用“自研”。
- 多文件/多改动时可分行书写，每条格式保持一致。
- 单行提交信息尽量不超过 100 个字符；如超过，应优先压缩“具体内容”，必要时拆成多行。
- 多文件提交时，优先按功能聚合，避免罗列所有文件名。
- 若无法从 diff 中推断业务含义，应先询问用户补充，不要编造需求来源或业务目的。
- 只有在用户明确选择“提交并推送”且 push 前再次确认后，才执行 `git push`。

## 7. 安全红线

绝对禁止的行为：

1. 在用户确认后仍偷偷添加未确认的文件
2. 使用 `git add -A` 或 `git add .` 批量添加（除非用户明确选择“所有改动”）
3. 将构建产物、缓存文件、配置文件等作为“附带改动”提交
4. 跳过 staged 文件确认步骤直接 commit
5. 在未得到用户明确确认的情况下执行 git push
6. 使用纯文本提问替代 `AskUserQuestion` 弹窗（违反第 0 章约束）
