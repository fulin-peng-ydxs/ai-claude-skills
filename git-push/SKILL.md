# Git 提交与推送

## 职责与边界

负责文件范围、暂存、提交和已授权的推送；提交消息生成统一调用 [git-commit-message-authoring](../git-commit-message-authoring/SKILL.md)，消息模板与格式规则由该技能维护。

本文维护范围、确认和 Git 写操作顺序；提交消息格式只由 git-commit-message-authoring 维护。先按调用模式解释后续确认步骤，非显式调用不新增确认节点。

## 输入与前置条件

### 0. 交互方式强制约束

#### 0.1 调用模式覆盖规则

- 仅当用户使用 `$git-push`，或明确要求“使用/调用 `git-push` 技能”完成任务时，才属于显式调用；仅说“提交”“推送”“提交并推送”，或讨论、审查、修改本技能，不属于显式调用。
- 显式调用时，保留本技能后续所有交互确认要求。
- 非显式调用时，不向用户询问文件范围、提交信息、staged 清单、提交方式或 push 确认；后续流程中的“确认”统一改为由 AI 结合用户要求、当前会话、`git status` 和 diff 自行核定，并依次继续执行。
- 非显式调用且用户未指定文件时，只选择能够可靠归属于当前任务的改动，排除无关改动、构建产物、缓存、敏感配置和用户已有 staged 内容；无法安全确定范围时停止并报告具体阻塞，不把判断问题转交用户。
- 非显式调用不扩大操作授权：用户只要求提交时不 push；用户明确要求推送或提交并推送时，提交成功后直接 push，不再二次询问。
- 本节优先于后续所有关于“必须向用户确认”“未确认不得继续”和“工具不可用时中止”的表述；这些表述仅适用于显式调用模式。

**所有需要用户确认或选择的步骤，必须使用当前运行环境自身提供的交互式提问或选择工具完成，不得绑定特定厂商或工具名称，也不得使用普通文字提问替代。**

适用范围

- 凡是流程中提到“向用户确认”“让用户选择”“等待用户确认”的所有节点

实现要求：

1. AI 必须先识别当前环境可用的交互式提问或选择工具，并在每个确认节点调用该工具，给出明确选项。
2. 调用前先展示必要上下文，包括文件清单、commit 摘要和 push 范围，再让用户选择。
3. 即使只是确认是否继续，也至少提供“继续”和“取消”两个选项。
4. 当前环境没有提供交互式提问或选择工具，或该工具不可用时，必须立即中止当前流程并说明原因；禁止改用普通文字、编号选项或其他非交互形式向用户提问。

不得因为工具名称或能力形态不同而跳过确认；不得假定用户已确认；违反此约束时必须立即中止后续操作。

## 执行流程

### 1. 确定提交文件范围

#### 1.1 用户主动指定文件
- 如果用户在请求中明确提到了要提交哪些文件（例如“提交 detail.vue”“只提交前端文件”“@ 对应文件”），则直接选择用户指定的文件。
- 严禁自作主张添加用户未提及的其他文件，即使用户提到的文件很少。

#### 1.2 用户未指定时提供选项
- 如果用户没有明确指定要提交的文件，则：
  1. 先运行 `git status --short` 查看当前有改动的文件。
  2. 再结合当前会话中实际编辑/修改过的文件，生成推荐列表并简要说明推荐原因。
  3. 向用户提供以下三个选项，让用户选择：
     ```
     请选择要提交的文件范围：
     1. 所有改动文件（共 X 个文件）
        - 列出所有改动文件（如某目录文件很多，则写“目录 + 文件数量”）
     2. 智能建议（推荐 X 个文件）
        - 业务说明
        - 文件 1（具体业务说明）
        - 文件 2（具体业务说明）
     3. 其他：用户自己说明要提交的文件
     ```
  4. 根据用户的选择确定要提交的文件清单。

#### 1.3 文件范围确认
- 在执行任何 `git add` 之前，必须先向用户列出准备提交的文件清单，例如：
  ```
  准备提交以下文件：
  - src/views/riskManagement/mechanismEffectScore/detail.vue（前端详情页添加返回按钮）
  - src/views/riskManagement/mechanismEffectScore/index.vue（前端列表页修复）
  ```
- 用户确认文件范围后，后续只能按该范围执行，禁止额外添加文件。

### 2. 生成提交信息并先确认

在执行 `git add` 之前，读取并调用 [git-commit-message-authoring](../git-commit-message-authoring/SKILL.md)，基于第 1 节已确定的范围生成提交消息；不得在本技能内另写模板或跳过该调用。依赖技能缺失或不可读时停止提交，说明缺口。

#### 调用约定

1. 读取范围内必要的 diff，理解改动目的；向 `git-commit-message-authoring` 传入文件清单、改动摘要、用户明确提供的来源与遵循文档，以及实际验证结果。
2. 若范围包含多个互不依赖的需求，显式调用本技能时先让用户选择“缩小范围后提交其中一个需求”或“仍按当前范围生成一次提交”；非显式调用时按第 0 节自行核定。一次流程只生成一条提交消息、执行一次 `git commit`。
3. 这里对 `git-commit-message-authoring` 的调用属于流程内部调用，按其非显式模式执行，复用已确定的范围与多需求处理结果，不重复询问；不会因为用户显式调用了 `git-push` 而变成显式调用 `git-commit-message-authoring`。
4. 消息模板选择、操作类型、项目标识、条件字段、多需求格式和输出约束均遵循 `git-commit-message-authoring`；本技能接收返回文案后继续执行后续提交步骤。

#### 提交信息确认

- 向用户展示生成的提交信息，并同时展示提交信息对应的文件范围和主要改动依据。
- 若用户认为文案不合适，先调整提交信息，再进入 `git add`。
- 在用户确认提交信息前，不执行 `git add`、`git commit` 或 `git push`。

### 3. 按确认范围执行 git add

#### 3.1 执行原则
- 根据用户确认的文件清单执行 `git add <文件路径>`。
- 只能添加用户明确确认的文件。
- 严禁使用 `git add -A` 或 `git add .` 等批量添加命令，除非用户明确选择“所有改动文件”。

#### 3.2 默认禁止附带添加的文件

除非用户明确提到，严禁添加以下类型文件：

- 前端构建产物（`static/`、`dist/`、`build/`）
- 包管理器缓存（`node_modules/`、`.pnpm-store/`、锁文件等）
- 配置文件（`pom.xml`、`bootstrap*.yml`、`.env*`、`application*.yml` 等）
- 其他业务模块文件
- IDE/编辑器配置（`.idea/`、`.vscode/`、`*.iml`）
- 日志/临时文件（`*.log`、`tmp/`、`*.tmp`）

#### 3.3 staged 最终确认

- 执行 `git add` 后，必须运行能清晰展示 staged 文件的命令，并向用户展示结果。
- 优先使用：
  - `git diff --cached --name-status`
  - 必要时补充 `git status --short`

- 向用户确认：
  ```
  已 staged 的文件如下（请确认只有你同意提交的文件）：
  <staged 文件清单>

  请确认：
  1. 文件清单正确，继续 commit
  2. 文件清单正确，直接 commit 并 push
  3. 文件清单有误，需要修正
  ```

- 只有用户确认 staged 文件清单正确后，才能继续执行 `git commit`。
- 如果用户选择“文件清单正确，直接 commit 并 push”，表示用户已同时确认当前 staged 文件清单、提交信息和推送动作；后续直接进入 `git commit` → `git push`，不再重复询问提交方式或 push 前确认。
- 用户选择“直接 commit 并 push”后，必须锁定当前 staged 清单：
  - 不得再执行任何 `git add`、`git add -A`、`git add .` 或其它会改变 staged 范围的命令。
  - `git commit` 前必须重新运行 `git diff --cached --name-status`，与刚才展示给用户确认的 staged 清单逐项对比。
  - 如果 staged 清单发生变化，必须中止直接提交推送流程，重新展示 staged 清单并让用户确认。

### 4. 确认提交方式并执行

#### 4.1 提交方式确认

在 staged 文件和提交信息都确认后，再向用户确认执行方式：

```text
提交信息：
<commit message>

请确认提交方式：
1. 仅提交（执行 git commit，不推送）
2. 提交并推送（执行 git commit → git push）
3. 其他：用户自己说明
```

#### 4.2 执行逻辑

- 如果用户选择 1，则执行 `git commit` 后停止。
- 如果用户选择 2，则执行 `git commit`，成功后再执行 `git push`。
- 如果用户选择 3，则按用户说明执行。
- 如果用户已在 3.3 选择“文件清单正确，直接 commit 并 push”，则跳过本节提交方式确认，按 3.3 的锁定 staged 清单规则执行 `git commit`，成功后直接执行 `git push`。

#### 4.3 push 前确认

- 如果用户选择“提交并推送”，则在 `git commit` 成功后、`git push` 之前，必须再次做一次最终确认：
  ```
  即将推送以下 commit：
  <git log -1 --stat>

  确认要执行 git push 吗？(yes/no)
  ```
- 只有用户明确确认后，才能执行 `git push`。
- 如果用户已在 3.3 选择“文件清单正确，直接 commit 并 push”，本节 push 前确认视为已由 3.3 完成；不得再次改动 staged 范围，只能推送刚刚创建的 commit。

### 5. 执行顺序（固定）

严格按以下顺序执行，不要打乱；**所有“确认”环节必须使用当前环境自身提供的交互式提问或选择工具；工具不可用时立即中止，禁止使用普通文字提问兜底**：

1. 确定文件范围
2. 展示并通过交互式提问或选择能力确认文件范围
3. 读取确认范围内的 diff 摘要
4. 若发现多个互不依赖需求，通过交互式提问或选择能力让用户选择缩小范围或继续生成单次提交信息
5. 生成提交信息并通过交互式提问或选择能力确认
6. 按确认范围执行 `git add`
7. 展示 staged 文件清单并通过交互式提问或选择能力确认
8. 如果用户在 staged 确认中选择“直接 commit 并 push”，重新校验 staged 清单未变化后执行 `git commit` → `git push`
9. 否则，通过交互式提问或选择能力确认提交方式
10. 执行 `git commit`
11. 若用户选择 push，则通过交互式提问或选择能力再次确认后执行 `git push`

## 核心约束

### 6. 注意事项

- 只有在用户明确选择“提交并推送”且 push 前再次确认后，才执行 `git push`；或用户在 3.3 staged 最终确认中明确选择“文件清单正确，直接 commit 并 push”后，才可跳过后续重复确认并直接推送刚刚创建的 commit。非显式调用按第 0 节已有推送授权执行。

### 7. 安全红线

绝对禁止的行为：

1. 在用户确认后仍偷偷添加未确认的文件
2. 使用 `git add -A` 或 `git add .` 批量添加（除非用户明确选择“所有改动”）
3. 将构建产物、缓存文件、配置文件等作为“附带改动”提交
4. 跳过 staged 文件确认步骤直接 commit
5. 在未得到用户明确确认的情况下执行 git push
6. 未使用当前环境自身提供的交互式提问或选择工具，或在工具不可用时改用普通文字、编号选项等非交互形式提问
7. 用户选择“直接 commit 并 push”后再次执行 `git add` 或提交与最终 staged 确认不一致的文件

## 产出边界与交付

交付本次提交标识、实际文件范围、提交或推送结果及失败原因。只提交不自动推送；推送失败保留已成功提交的状态，不把 commit 成功称为 push 成功。

## 验证与完成标准

提交前核对暂存范围与授权一致，执行顺序按第 5 节；提交后检查实际 commit，推送后检查命令结果与远端状态。任何失败明确指出停在哪一步，保护用户原有改动与暂存内容。
