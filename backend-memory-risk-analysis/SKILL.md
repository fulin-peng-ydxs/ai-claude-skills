# 后端内存风险分析

## 职责与边界

本文维护分析范围、证据分级、连续报告和交付规则；[内存风险清单](references/memory-risk-checklist.md) 维护具体风险模式，生成报告时按下文读取产物模板。默认分析与产档，不因发现风险自动修改代码或生产运行参数。

### 概览

使用这个技能分析项目后端代码中可能存在的内存溢出、内存泄漏和持续内存增长风险，并输出完整报告。

默认做代码级风险分析，而不是伪装成运行时已确认结论。若没有 heap dump、profiler 输出、GC 日志或生产监控指标，应把结论表述为“疑似风险”或“潜在风险”，并给出置信度和后续验证建议。

风险模式见 `references/memory-risk-checklist.md`；报告路径、基线与状态规则由本文维护。

## 输入与前置条件

### 第一步：锁定范围

先识别需要分析的后端模块。

优先顺序：

1. 用户明确指定的后端模块或服务路径。
2. 常规后端目录，例如 `src/main/java`、`server`、`service`、`listener`、`scheduled`、`config`、`util`、`dao`、`repository`。
3. 与运行时强相关的代码，例如调度任务、监听器、缓存、MQ 处理器、批处理任务、上传导出逻辑、集成层。

如果仓库是前后端混合项目，除非为了理解后端引用链，否则不要扩展到前端代码。

## 执行流程

### 工作流

1. 锁定后端分析范围。
2. 识别后端运行形态和长生命周期组件。
3. 检查高风险内存模式。
4. 按证据强度分级和判定。
5. 输出并落盘完整风险报告。

### 第二步：识别运行形态

在找泄漏前，先识别这个后端里“什么对象可能被长期持有”。

至少要明确：

1. 语言和运行时：
- Java/Spring Boot、Node.js、Go、Python 或其他。
2. 长生命周期组件：
- 单例服务、静态持有对象、缓存、调度器、监听器、线程池、MQ 消费者、WebSocket/会话管理器。
3. 数据密集型路径：
- 大查询、导入导出、文件处理、JSON 序列化、批量聚合、内存内 Join、流式缓冲。
4. 外部集成点：
- Redis、MQ、MQTT、WebSocket、Feign/HTTP 客户端、TDengine/MySQL、文件存储、视频流、规则引擎。

对于 Java/Spring 项目，优先检查单例 Bean、静态集合、`ThreadLocal`、线程池队列、定时任务、监听器和大集合处理路径。

### 第三步：检查内存风险模式

读取 [内存风险清单](references/memory-risk-checklist.md)，按本次语言、长生命周期组件和数据密集型路径选择风险模式及检索词。搜索结果只提供候选线索，判断必须回到具体代码证据；风险等级按下文统一判定。

## 核心约束

### 第四步：分级与判定

不要把每一处可疑代码都直接说成“内存泄漏”，要先分级。

统一使用以下分级：

1. `High Risk`
- 有明确代码证据表明对象会长期存活或无限增长。
2. `Medium Risk`
- 有明显增长风险，但触发条件或清理逻辑还不够明确。
3. `Low Risk`
- 模式值得关注，但当前代码证据偏弱。
4. `Needs Runtime Evidence`
- 风险合理存在，但需要 heap dump、profiler、GC 日志、分配火焰图或生产监控进一步确认。

每条风险都必须说明：

1. 可能被持有的对象或数据是什么。
2. 为什么它会持续增长或存活过久。
3. 在什么触发条件下会变得危险。
4. 代码里有什么证据。
5. 首先应该改什么。

### 执行规则

1. 优先使用具体代码证据，而不是宽泛架构猜测。
2. 没有运行时证据时，必须写成“疑似风险”或“潜在风险”。
3. 优先关注长生命周期对象持有，而不是短生命周期分配噪声。
4. 对 Java/Spring 后端，先检查调度任务、监听器、缓存、执行器、单例服务和大集合处理。
5. 当未发现明显风险时，也要明确写出“暂未发现明显风险”和剩余盲区。
6. 每条风险必须带处理进度字段，统一使用以下状态之一：
- `已处理`
- `未处理`
- `业务需要`
- `不重要`
- `需运行时验证`
7. 默认不要把每天的报告写成相互孤立的快照，而要基于“上一份最新报告 + 本次代码现状”形成连续演进记录。

## 产出边界与交付

首次生成或获准补全文档时落实下述产物边界；仅保存、逐字保存或局部更新沿用有效基线，不为补边界扩写或重排，范围外缺口在交付中说明。

### 产出文档边界

文档边界遵循 [全局规范](~/ai-agent-config/config/force/document-boundaries.md)。报告维护指定后端范围的内存风险、证据、触发条件、验证缺口与处理状态，并说明本次检查时间和基线；不承载完整模块架构或通用运维手册。

### 第五步：输出并落盘报告

输出必须是完整报告，而不是零散结论。

报告必须包含：

1. 分析范围
- 检查了哪些后端模块。
2. 运行形态摘要
- 语言、框架、长生命周期组件、主要风险面。
3. 风险清单
- 按风险等级排序。
4. 总体判断
- 是否存在明显 OOM/泄漏风险。
5. 处理进度
- 每条风险的当前状态。
6. 下一步建议
- 代码修复、运行时验证和监控建议。

报告路径与基线选择：

1. 用户指定路径或项目已有明确约定优先；未指定时先检查同一后端范围的已有内存报告，包括 `docs/check/memory` 和旧入口 `doc/check/memory`，沿用已建立的报告目录。只有确无已有成果时，才使用默认 `docs/check/memory/{日期}.md` 并按需创建目录，不因默认路径变化迁移文件或另起一套报告。
2. `{日期}` 默认使用当天日期，建议格式为 `YYYY-MM-DD`。新指定输出位置也不免除读取同范围已有基线，报告中记录来源路径。
3. 生成前读取同一后端范围最新的有效报告作为基线。两个目录都有成果时，结合检查日期、范围、相互引用及状态证据识别当前维护主线，不以文件修改时间直接覆盖较完整记录；其它同范围报告中仍有效的风险须核对去向。无法消解的状态冲突保留并说明，不默认为已处理；无法确定维护主线时先确认目标，不擅自合并或丢弃已有成果。
4. 对最新已有报告中的风险项，结合当前代码现状更新其处理进度、风险等级、代码证据和建议。
5. 若本次扫描发现之前报告中没有的新风险，则在本次报告中新增这部分风险项。
6. 若同日期报告已存在，则在该文件上继续增量更新，不要盲目覆盖有效内容。
7. 除非用户另有要求，最终结果应以报告文件为主，而不是只在聊天中给摘要。

### 报告模板

按 [文档结构与输出规范](~/ai-agent-config/config/force/document-output.md) 使用**默认骨架**。分析范围与基线、总体结论、逐项风险证据和处理进度、验证缺口与后续建议必须可辨识；每条风险的必填字段、编号、状态枚举及追溯关系保持固定，无风险时说明检查范围与盲区，不生成空风险项。


以单条风险组织代码依据、增长机制、触发条件、处理判断和复核路径；跨风险共用盲区及后续安排集中维护。

生成对应完整产物或获准补全本部分时，读取 [内存风险报告](references/output-template.md#内存风险报告)；仅保存或局部更新不重新套版。

## 验证与完成标准

逐项核对长期持有对象、增长原因、触发条件、代码证据、影响、建议和处理状态；回查上一份报告，区分新增风险与状态变化。没有运行时证据不得声明泄漏已证实，未发现明显风险仍说明盲区。
