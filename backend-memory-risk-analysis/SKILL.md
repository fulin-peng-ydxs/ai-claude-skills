# 后端内存风险分析

## 职责与边界

本文维护分析范围、证据分级、连续报告和交付规则；[内存风险清单](references/memory-risk-checklist.md) 维护具体风险模式，生成报告时按下文读取产物模板。默认分析与产档，不因发现风险自动修改代码或生产运行参数。

### 概览

使用这个技能分析项目后端代码中可能存在的内存溢出、内存泄漏和持续内存增长风险，并输出完整报告。

默认做代码级风险分析，而不是伪装成运行时已确认结论。若没有 heap dump、profiler 输出、GC 日志或生产监控指标，应把结论表述为“疑似风险”或“潜在风险”，并给出置信度和后续验证建议。

风险模式见 `references/memory-risk-checklist.md`；报告路径、基线与状态规则由本文维护。

## 输入与前置条件

### 分析范围

先识别需要分析的后端模块。

优先顺序：

1. 用户明确指定的后端模块或服务路径。
2. 常规后端目录，例如 `src/main/java`、`server`、`service`、`listener`、`scheduled`、`config`、`util`、`dao`、`repository`。
3. 与运行时强相关的代码，例如调度任务、监听器、缓存、MQ 处理器、批处理任务、上传导出逻辑、集成层。

如果仓库是前后端混合项目，除非为了理解后端引用链，否则不要扩展到前端代码。

## 执行流程

仅保存已有报告时，核对原文、有效修正和目标路径后保存，不重新分析或改变证据状态。局部更新只执行受影响步骤；首次分析或完整复查按以下顺序进行。

1. **确定范围与基线**：按前置条件锁定后端模块，按“报告路径与基线”找到同范围最新有效报告和目标文件。先核对已有风险及维护主线，再开始本次分析；混合项目仅追踪理解后端所需的前端引用。
2. **识别运行形态**：确定语言与运行时、长生命周期组件、数据密集型路径和外部集成点，重点判断哪些对象可能被长期持有：
   - 语言与运行时：Java/Spring、Node.js、Go、Python 等实际技术栈。
   - 长生命周期组件：单例、静态集合、缓存、调度器、监听器、线程池、MQ 消费者和 WebSocket/会话管理器。
   - 数据路径：大查询、导入导出、文件处理、JSON 序列化、批量聚合、内存内 Join 和流式缓冲。
   - 外部集成：实际使用的 Redis、MQ/MQTT、HTTP 客户端、数据库、文件存储、视频流或规则引擎等。
3. **追踪风险与证据**：读取 [内存风险清单](references/memory-risk-checklist.md)，按实际语言、组件和数据路径选择检查项。搜索只产生候选线索，必须回到持有对象、增长或释放机制及触发条件；Java/Spring 优先检查单例 Bean、静态集合、ThreadLocal、线程池队列、定时任务、监听器和大集合处理。
4. **判定风险与状态**：按“风险与状态判定”分别填写风险等级、证据状态、处理状态和处置决定，关联证据与验证缺口；核对旧风险的延续、变化及新增项，不把代码线索当作已发生的运行时泄漏。
5. **编写、核对与交付**：读取 [报告模板](references/output-template.md)，按确定的路径形成完整报告；沿用稳定风险编号，按“验证与完成标准”回查内容后保存，交付文件、主要结论及剩余盲区。用户只要求对话结论时按其要求交付，不自动落盘。

## 核心约束

### 风险与状态判定

不要把每一处可疑代码都直接说成“内存泄漏”，要先分级。

风险等级与证据状态分别记录，不用缺少证据代替影响等级：

- **风险等级**：`High Risk`、`Medium Risk`、`Low Risk` 或 `待判定`。按有依据的触发条件、影响范围与资源耗尽后果判断：High 表示预期负载下可能持续耗尽资源或导致服务不可用，Medium 表示特定条件下明显增长且影响相对可控，Low 表示影响有限、优先级较低；均说明依据。无法判断影响时用待判定，不能因证据弱自动降为低风险。
- **证据状态**：`代码证据`、`运行时已证实`、`证据不足`。代码证据可确认持有或增长机制，不能据此宣称运行时泄漏已发生；运行时已证实须有相关采样及因果依据。缺口与后续验证方法单独说明。
- **处理状态**：`未处理`、`处理中`、`已修复待验证`、`已验证解决`。修复与验证分别给依据；没有实际复核不能标为已验证解决。
- **处置决定**：`待决定`、`安排修复`、`接受风险`、`暂缓处理`。接受或暂缓须记录决策来源、理由、适用条件及复查触发，不能因技术分析自行替用户接受风险。

等级、证据、进度及处置相互独立，例如“高风险／代码证据／已修复待验证／安排修复”可以同时成立。

已有报告仅保存时保留原状态。更新风险项时依据证据解释旧值：`需运行时验证` 表达验证缺口，不能推定风险等级或处理进度；`业务需要`、`不重要` 只提供处置理由线索，未有明确决定不能自动转为接受风险；`已处理` 须区分是否有修复及复验证据。无法映射时保留原值并标待核实，不批量重标历史成果。

### 证据与分析原则

1. 优先使用具体代码证据，而不是宽泛架构猜测。
2. 没有运行时证据时，必须写成“疑似风险”或“潜在风险”。
3. 优先关注长生命周期对象持有，而不是短生命周期分配噪声。
4. 当未发现明显风险时，也要明确写出“暂未发现明显风险”和剩余盲区。
5. 每条风险分别记录上述风险等级、证据状态、处理状态和处置决定，并关联依据。
6. 默认不要把每天的报告写成相互孤立的快照，而要基于“上一份最新报告 + 本次代码现状”形成连续演进记录。

## 产出边界与交付

首次完整报告读取 [内存风险报告](references/output-template.md)，由模板统一维护结构、最低内容、字段和产物边界。报告反映本次证据，不因发现风险自动修代码或更改生产参数。

### 报告路径与基线

1. 用户指定路径或项目已有明确约定优先；未指定时先检查同一后端范围的已有内存报告，包括 `docs/check/memory` 和旧入口 `doc/check/memory`，沿用已建立的报告目录。只有确无已有成果时，才使用默认 `docs/check/memory/{日期}.md` 并按需创建目录，不因默认路径变化迁移文件或另起一套报告。
2. `{日期}` 默认使用当天日期，建议格式为 `YYYY-MM-DD`。新指定输出位置也不免除读取同范围已有基线，报告中记录来源路径。
3. 生成前读取同一后端范围最新的有效报告作为基线。两个目录都有成果时，结合检查日期、范围、相互引用及状态证据识别当前维护主线，不以文件修改时间直接覆盖较完整记录；其它同范围报告中仍有效的风险须核对去向。无法消解的状态冲突保留并说明，不默认为已处理；无法确定维护主线时先确认目标，不擅自合并或丢弃已有成果。
4. 对最新已有报告中的风险项，结合当前代码现状更新其处理进度、风险等级、代码证据和建议。
5. 若本次扫描发现之前报告中没有的新风险，则在本次报告中新增这部分风险项。
6. 若同日期报告已存在，则在该文件上继续增量更新，不要盲目覆盖有效内容。
7. 除非用户另有要求，最终结果应以报告文件为主，而不是只在聊天中给摘要。

仅保存或局部更新保留授权基线，不重新套版。继续分析时逐项核对已有风险与实际状态，沿用稳定编号，补充有效新证据。

## 验证与完成标准

逐项核对长期持有对象、增长原因、触发条件、代码证据、影响、建议和处理状态；回查上一份报告，区分新增风险与状态变化。没有运行时证据不得声明泄漏已证实，未发现明显风险仍说明盲区。

首次完整报告或整体重构后运行 `python3 <skills-root>/skill-authoring-standard/scripts/validate_document_template.py <产物路径> --template <本技能目录>/references/output-template.md`；字段内容按同一模板核对，保存和局部更新不借格式检查重排全文。
