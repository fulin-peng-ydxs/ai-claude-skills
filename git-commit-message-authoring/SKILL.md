# Git 提交消息编写

## 职责与边界

只根据确定的改动范围生成一条提交消息，不执行 `git add`、`git commit` 或 `git push`。本文维护范围选择和消息生成流程；[提交消息格式与示例](references/commit-message-format.md) 维护格式、类型、模板及来源规则。实际提交流程由调用方负责。

## 输入与前置条件

先识别调用方式：

| 方式 | 范围处理 |
| --- | --- |
| 提交流程内部调用 | 接收调用方确定的文件、改动摘要、多需求处理决定、明确来源与文档、实际验证结果；只分析传入范围，不再次询问。调用方显式使用其他技能，不等于显式调用本技能。 |
| 普通请求 | “生成提交信息”“写 commit message”等请求，按指定文件或当前任务及 Git 差异自行核定范围；不询问范围或文案。无法可靠确定范围或业务含义时报告证据缺口，不编造或扩大范围。 |
| 用户显式调用 | 仅指 `$git-commit-message-authoring` 或明确要求使用本技能；按下述显式范围确认执行。讨论、审查或修改本技能不属于调用。 |

### 显式范围确认

仅显式调用需要此分支：先读取 `git status --short`，按指定文件或会话改动提出范围，展示文件及用途。未指定范围时提供“全部改动”“推荐的任务相关改动”及自定义范围的选择，随后取得范围确认。多个独立需求建议拆分范围，让用户选择缩小到一个需求或按当前范围生成一条消息。

上述确认使用当前环境的交互式提问工具，提供可继续及取消/调整的选择；工具不可用时停止并说明，不以普通文字提问替代。已有精确覆盖本次范围及多需求处理的确认直接复用；此工具要求不适用于普通请求和内部调用。

## 执行流程

1. 按调用方式确定范围，不额外分析或加入范围外文件。
2. 阅读范围内必要的 diff，识别业务目的、操作类型、影响及实际验证；不按文件名猜测目的，不编造需求来源。
3. 读取 [提交消息格式与示例](references/commit-message-format.md) 并生成一条消息。多个文件服务同一需求时按能力聚合；确定合并多个独立需求时采用模板 B 和 `Agent 操作类型(多模块): ...`，主要改动分组表达，不堆叠多个标题。
4. 直接交付文案，不增加生成后的确认节点。内部调用将消息返回调用方，由其继续已经授权的提交流程。

## 核心约束

项目标识默认 `Agent`，只有用户指定简写时替换。无明确需求来源或遵循文档时省略对应段落；多文件按业务能力聚合，保留实际验证与限制。一次调用只生成一条消息，不自行拆为多次提交，不因生成消息获得 Git 写入授权。

## 产出边界与交付

独立调用直接输出最终提交文案；用户未要求时不输出 `git commit -m` 命令。内部调用不结束调用方的任务，也不代为暂存、提交或推送。

## 验证与完成标准

核对消息与确定范围内的 diff 一致，模板、操作类型、来源及验证陈述符合格式契约；范围外文件未被加入，无虚构来源或执行结果。
