# 需求闭环设计

## 职责与边界

本技能补全需求在系统中如何跑通：功能链路、角色、状态、范围和未决事项；不承担正式需求编制或开发实施拆分。

本文维护闭环分析流程、最低业务内容和完成标准；[产物模板](references/closure-template.md) 维护输出骨架与字段，调研、确认和保存规则由下述共用契约维护。

## 输入与前置条件

输入为用户的粗需求、当前闭环成果及相关项目依据；先定位目标项目、当前讨论对象和已有确认状态。缺失事实先调研，影响闭环成立的业务选择按共用契约处理。

执行前读取 [需求协作共用契约](../requirement-doc-authoring/references/workflow-contract.md)，继承调研、确认、保存和自适应规则；无需读取正式需求技能全文。

## 执行流程

先识别操作与基线，继承已有成果和有效确认；按下表执行对应分支，不将完整分析作为保存、局部修改或阶段切换的前置。

| 用户意图 | 执行动作 |
| --- | --- |
| 首次分析、继续细化闭环 | 调研范围内的项目事实，按“核心约束”补全闭环，区分事实、推断和未决项；首次完整分析使用产物模板，继续细化维护当前基线。走读代表性场景后在对话中交付；没有保存请求时不建目录或文件。 |
| 明确确认闭环无问题、可落地，或要求保存 | 核对所指成果及后续有效修正，按共用契约保存为 `requirement-closure.md`；路径可确定就直接执行。不重新调研或补全，草案与未决状态如实保留；仅认可方向不视为完整闭环获批。 |
| 局部修改、重构 | 仅在获准范围调研、修改和核对受影响内容及引用；局部修改保留原结构，重构按授权调整。发现范围外缺口在交付中报告，不自动补全。 |
| 明确要求正式需求文档、PRD 或 requirement.md | 直接交接到 [requirement-doc-authoring](../requirement-doc-authoring/SKILL.md)，携带已有结论、依据和未决项，不先重跑闭环分析。 |

完成所选分支后，按对应的验证与交付要求结束本次工作，不自动推进下一阶段。

## 核心约束

### 分析与最低内容

按共用契约读取全局阅读组织规则，以业务环节为详细说明单元。开头说明目标、范围摘要、成熟度和关键待决事项；正文采用“业务闭环总览→按业务环节展开→范围与待决事项”的默认骨架。功能范围及建议状态在范围索引维护，待决摘要链接所属环节，跨环节共用选择在待决区完整维护。

先调研可验证事实，再补齐下列适用信息；这些是信息要求，不要求分别设章：

- **目标与范围**：解决什么问题，必须实现、建议实现、暂不实现分别是什么；建议项沿用共用状态与互斥规则。
- **角色与入口**：谁能用，从哪里进入，前置条件、权限和配置如何影响操作。
- **完整链路**：主链路、关键支链路、操作与反馈、状态变化、结果保存和生效、交接对象、失败位置、继续或回退方式，以及怎样判断闭环成立。
- **功能清单**：范围索引逐项列出功能业务名称及所属环节；环节内各功能点的目标、入口、关键操作、反馈、状态、权限/配置、异常独立可辨识，不因按环节整合而丢失支线功能。
- **页面承载**：涉及页面、弹窗、抽屉或配置入口时，明确各自职责、跳转/联动/回流、数据变化、空态和失败反馈；只有影响闭环才展开接口、数据或上下游机制。
- **结论与未决**：项目事实、已确认结论、推断依据、阻塞与非阻塞项可区分；每个问题说明影响、推荐选择与理由、确认时点及阻塞环节，相关推断和选择就地说明。

多个环节共用页面时集中说明页面职责、跳转/回流及共用状态，环节只补特有行为；单环节页面信息直接并入该环节。闭环成立的判断是业务行为判断，不扩成正式验收表。

页面阶段不提前细化字段顺序、按钮位置、列宽、样式和微文案；但影响业务成立的入口、操作、权限和反馈不能留待 PRD 才补。

### 专项工作在闭环阶段的承载

仅在当前请求涉及相应业务闭环时补入已有目标、链路或边界，不另套技术方案模板：

- 缺陷修复说明预期与实际差异、触发条件和受影响角色/链路，明确恢复后的正确行为；未证实的原因保留为假设。重构/升级说明需保持的业务行为及允许变化，不因技术替换重新设计业务。
- 数据迁移/补数/修复明确目标数据范围、正确口径、历史与新增数据如何衔接、结果由谁消费，以及失败或差异由谁处理。异步/第三方链路区分受理、处理中和业务终态，明确重复操作、超时、部分成功的用户反馈与适用的恢复/人工接管，不能把请求成功当作业务完成。
- 从零建设先确定最小可用业务闭环与暂不建设范围；技术验证仅承载其需证明的业务假设和成功/失败边界。纯内部重构或技术验证若没有业务闭环变化，说明范围即可，不虚构角色、页面或功能点。

## 产出边界与交付

闭环阶段不分配正式需求编号，不自动生成 `requirement.md`、`prototypes/`、正式验收表或开发计划，也不提前展开性能、安全、兼容性专章。会影响业务成立的容量、安全或兼容边界仍须讨论，不能因不设专章而遗漏。

用户同时要求技术方案等复合成果时，首次输出分区承载，保存时完整保留；业务闭环部分只确定必要行为、边界和外部契约，类、函数、索引与内部事务编排留在技术方案部分，不升级为业务要求。

首次完整分析时读取 [需求闭环产物模板](references/closure-template.md)，采用默认骨架，按共用契约合并相近章节或裁剪不适用内容，每个功能点仍须独立可辨识。保存已有成果不重套模板。

默认在对话中交付；满足上表保存条件时，按共用契约确定目录并保存为 `requirement-closure.md`，用户指定优先。产物包含闭环、范围、依据和未决项。首次生成或获准补全长期闭环文档时，在用途说明中明确：本成果维护业务闭环，正式编号与验收契约归需求文档，实施拆分归开发计划；仅保存、逐字保存或局部修改时保留授权基线，不为补边界扩写或重排；缺失说明在交付中报告。

## 验证与完成标准

- 分析或获准补全时，按一条代表性场景核对操作、反馈、结果、交接和失败恢复；局部修改只复核受影响链路，仅保存时对照原基线检查内容、引用和确认状态，不重新补全。不能靠章节齐全证明闭环。
- 核对功能范围索引能定位每个环节和独立功能点，角色操作、页面承载、状态交接与失败恢复同链可读；待决摘要能回到选择依据，阻塞与非阻塞不因合表而混淆。
- 范围不交叉，建议有状态，关键前提未知时不伪装成已闭环；生成成果按用户目标检查，保存成果按原基线检查。
- 保存后报告路径、新建或更新及遗留项，结束本次授权工作，不顺带生成正式需求、原型或计划。
