# Auto Code Dev

按“需求确认 -> 读取规则 -> 上下文分析 -> 计划确认 -> 编码 -> 自审 -> 脚本验证 -> 汇报”的闭环执行通用代码开发任务。

## 0. 执行流程总览

1. 触发判断：只有用户明确点名 `auto-code-dev` 时启用。
2. 需求确认：读取用户本次口述需求和用户指定的需求文档、开发计划、Issue、接口文档等需求来源。
3. 规则读取：读取 `agent/code/general-rule.md` 和用户指定的额外规则文件。
4. 上下文分析：按任务需要读取相关代码、接口、页面、实体、配置、调用链或数据库结构；上下文不足时先提问。
5. 计划输出：说明需求理解、实施范围、规则落地、验证方案、风险边界和待确认点。
6. 用户批准：只有用户明确输出 `批准开发计划` 后编码。
7. 编码实施：按批准计划小范围改动，复用项目既有结构和风格。
8. 自审修正：检查需求、规则、边界、权限、数据、兼容性和测试必要性。
9. 脚本验证：只使用 `agent/verify` 下的项目验证脚本，并按改动风险选择验证层级。
10. 失败闭环和汇报：相关失败必须修复并重跑；最终说明完成情况、文件、规则满足和验证结果。

## 1. 计划与规则确认

只有用户明确点名调用 `auto-code-dev` 技能时，才使用本技能；不能根据开发、修改、修复或重构类任务自动采用。

用户明确调用本技能后，先进入计划模式，不得直接改代码。

### 1.1 需求来源确认

生成开发计划前，必须先明确本次需求来源：

- 用户本次口述需求是最低输入。
- 用户指定的需求文档、开发计划、Issue、接口文档、截图或验收说明必须读取。
- 未提供需求文档时，可以基于用户口述需求继续，但计划中必须整理目标、范围、验收点和未知点。

需求目标、影响范围、验收标准、关键业务规则不明确时，先向用户确认，不得把未确认的假设写成已确定计划。

### 1.2 规则读取

生成开发计划前，必须先读取项目根目录：

- `agent/code/general-rule.md`

如果用户指定了额外规则文件，也必须一并读取并遵守；未指定时只使用 `agent/code/general-rule.md`。

如果规则文件不存在、路径不可读，或规则内容与用户需求存在冲突，先向用户说明阻塞点和建议处理方式，不得自行忽略规则继续开发。

本技能只规定读取规则和执行门禁；具体质量标准以 `agent/code/general-rule.md` 及用户指定规则文件为准，避免在技能中重复复写通用规则。

### 1.3 上下文读取

生成开发计划前，必须按任务需要读取足够的项目上下文。常见上下文包括相关业务代码、调用方、接口定义、实体/DTO、页面组件、路由、配置、SQL、测试和同类实现。

上下文读取以能支撑计划为准，不机械扩大范围。若缺少上下文会影响实施范围、兼容性、验证方案或风险判断，必须先补读；仍无法确认时向用户提问。

### 1.4 计划内容

开发计划应覆盖本次开发所需的关键信息，可根据任务复杂度精简表达，避免机械套模板。通常需要说明：

- 需求理解：本次要解决的问题、涉及范围和预期结果。
- 实施思路：准备修改的模块、文件或核心逻辑。
- 规则落地：本次已读取的规则文件，以及其中与任务直接相关的要求如何落实。
- 上下文依据：已读取的需求来源和关键代码上下文，以及仍需用户确认的未知点。
- 验证方案：准备执行的验证脚本、参数和选择原因，脚本范围必须与本次改动类型匹配。
- 风险边界：可能影响的功能范围、兼容性风险或需要用户确认的点。

对于非常小的改动，可以合并表达；但不得省略需求来源、规则读取情况、批准条件和验证脚本选择。

### 1.5 批准条件

只有当用户明确输出 `批准开发计划` 后，才开始编码。

用户的其他表述，例如“可以”“继续”“按这个来”“没问题”等，只能视为继续讨论或要求调整计划，不得视为开发批准。

## 2. 编码实施

获得 `批准开发计划` 后，按已批准计划和已读取规则实施改动。

实施时优先复用项目现有分层、命名、工具函数、异常处理和返回结构；不要引入与本次需求无关的新依赖、新抽象或大范围重构。若开发过程中发现计划遗漏、需求假设变化、实现范围变化或需要降低验证范围，先暂停并向用户说明调整点，等待新的确认后再继续；若只是增强验证范围且不改变需求和代码范围，可说明原因后继续执行。

## 3. 开发后自审

开发完成后，先通读自己改过的代码及直接关联代码，不执行验证命令。自审重点：

- 是否满足已批准计划和用户需求。
- 是否符合 `agent/code/general-rule.md` 及用户指定规则。
- 是否存在明显的边界条件、空值、异常处理、性能或资源释放问题。
- 权限、租户、数据范围、接口路径、状态值、字段含义、错误语义是否沿用项目既有机制。
- 前后端或多模块联动时，调用方、实现方、数据结构和边界行为是否一致。
- 成功路径、失败路径、空数据、重复操作、历史数据和兼容场景是否被考虑。
- 是否需要新增或修改测试；若不补测试，最终汇报中说明原因。
- 是否引入与本次任务无关的格式化、重构或行为变化。

发现问题就先修复，再重新自审；自审通过后才能进入脚本验证。

## 4. 只能用脚本验证

不要自行拼接或改用 `mvn`、`pnpm`、`npm`、`tsc`、`eslint` 等命令验证。只能调用项目已配置的验证脚本。

脚本失败时，先判断失败是否由本次改动引起：

- 若与本次改动相关，修复代码后重新自审并重跑对应脚本。
- 若是验证脚本配置、环境依赖或历史存量问题，说明证据和影响范围；只有在确认为脚本配置问题且属于本次验证必要范围时，才修复脚本配置。
- 若失败原因需要用户提供信息或决策，停止继续猜测并向用户说明阻塞点。

若本次需求涉及业务流程正确性，仅编译、静态检查或页面巡检不足以证明功能成立时，应优先使用项目已有测试或验证脚本补充覆盖；当前验证体系没有对应脚本时，在最终汇报中说明未覆盖的业务验收点和原因。

### 后端验证

改动 Java/后端代码时：

- 未新增或修改测试代码：
  - 编译整个项目：`bash ./agent/verify/scripts/java/mvn-compile.sh`
  - 后端在子目录：`bash ./agent/verify/scripts/java/mvn-compile.sh -r 后端目录`
  - 编译指定模块：`bash ./agent/verify/scripts/java/mvn-compile.sh -m 模块名`
  - 后端在子目录且指定模块：`bash ./agent/verify/scripts/java/mvn-compile.sh -r 后端目录 -m 模块名`
  - 清理再编译：`bash ./agent/verify/scripts/java/mvn-compile.sh --clean`
  - 指定 Maven settings：`bash ./agent/verify/scripts/java/mvn-compile.sh -s /path/to/settings.xml`
- 已新增或修改测试代码：
  - 测试整个项目：`bash ./agent/verify/scripts/java/mvn-test.sh`
  - 后端在子目录：`bash ./agent/verify/scripts/java/mvn-test.sh -r 后端目录`
  - 测试指定模块：`bash ./agent/verify/scripts/java/mvn-test.sh -m 模块名`
  - 后端在子目录且指定模块：`bash ./agent/verify/scripts/java/mvn-test.sh -r 后端目录 -m 模块名`
  - 测试类：`bash ./agent/verify/scripts/java/mvn-test.sh -c 测试类名`
  - 测试方法：`bash ./agent/verify/scripts/java/mvn-test.sh -c 测试类名 --method 方法名`
  - 测试模块和方法：`bash ./agent/verify/scripts/java/mvn-test.sh -m 模块名 -c 测试类名 --method 方法名`
  - 指定 Maven settings：`bash ./agent/verify/scripts/java/mvn-test.sh -s /path/to/settings.xml`

优先选择覆盖本次改动的最小充分脚本参数。若项目根目录没有 `pom.xml`，或本次改动位于某个后端服务子目录，先带 `-r/--root` 指向该 Maven 项目目录；多模块项目中能确定模块时再带 `-m`；项目明确需要私服或特殊 Maven 配置时再带 `-s/--settings`，默认不要添加 settings 参数。

### 前端验证

改动 Vue/前端代码时默认调用静态检查：

```bash
node ./agent/verify/scripts/vue/ai-check.js [改动文件...]
```

如果不传文件，脚本会自动读取 Git 工作区中的前端改动文件。默认只执行 lint/typecheck，不启动页面自动化，不要求 Playwright 或 token。

前端目录由 `agent/verify/scripts/vue/ai-config.json` 的 `frontendDir` 决定。前后端放一起时，`frontendDir` 可以指向服务目录；前后端分开时，`frontendDir` 应指向实际前端目录。传入文件参数时使用相对项目根目录的文件路径，并确保文件位于 `frontendDir` 下。

用户明确要求构建验证，或任务涉及打包、资源路径、环境变量、路由懒加载、构建配置时，追加 `--build`：

```bash
node ./agent/verify/scripts/vue/ai-check.js --build [改动文件...]
```

用户明确要求页面自动化验证，或本次改动确实涉及页面/组件渲染、登录态、接口联动、关键业务页、白屏风险时，追加 `--page`：

```bash
node ./agent/verify/scripts/vue/ai-check.js --page [改动文件...]
```

`--page` 用于页面可用性巡检，主要覆盖页面打不开、登录态失效、控制台错误、页面异常、HTTP 500、白屏和截图留存。若任务涉及表单提交、增删改查、流程状态流转或业务数据正确性，`--page` 不能替代业务断言；需要在计划和最终汇报中说明额外验收路径。

只有执行页面自动化时才需要 Playwright。若脚本提示缺少 Playwright，先执行：

```bash
bash ./agent/verify/scripts/install-vue-check-deps.sh
```

页面访问范围由 `agent/verify/scripts/vue/page-map.json` 决定；新项目首次接入或路由变化后，可执行 `node ./agent/verify/scripts/vue/update-page-map.js` 更新映射。若脚本配置可能不适配当前项目，可先执行 `node ./agent/verify/scripts/check-verify-config.js` 做配置自检；路径、目录、配置文件找不到等问题，查看 `agent/verify/PATH-TROUBLESHOOTING.md`。若同时改动前后端，后端脚本和前端脚本都要执行。

## 5. 最终汇报

最终回复按任务复杂度组织，避免机械套模板，但必须让用户看清以下信息：

- 计划完成情况：说明已完成、调整或未完成内容。
- 涉及文件：只分类列与本次任务相关的文件。
- 开发要求满足情况：说明是否符合 `agent/code/general-rule.md` 及用户额外指定的规则。
- 测试取舍：说明是否新增或修改测试；未补测试时说明原因。
- 脚本验证结果：列出实际执行的脚本、参数和通过/失败结论；失败后已修复并重跑的，也要说明最终通过结果。

对于很小的改动，可以用一段话合并汇报；对于范围较大的改动，应分点说明。

## 红线

- 未读取 `agent/code/general-rule.md` 前不得输出开发计划。
- 未确认基本需求来源、目标、范围和验收点前不得输出开发计划。
- 未得到 `批准开发计划` 前不得改代码。
- 不得跳过 `agent/code/general-rule.md` 或用户指定的额外规则文件。
- 不得把未确认的关键假设写成已确定计划。
- 不得用自由命令替代验证脚本。
- 不得未自审就进入验证或交付。
- 不得随意修改验证脚本来掩盖代码问题。
- 不得把脚本失败直接当作最终结果，除非失败原因需要用户提供信息或决策。
