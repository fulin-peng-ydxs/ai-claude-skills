# 项目发现与边界判断

## 先识别交付形态

不要默认当前目录就是单一应用或单一 Git 仓库。先判断它属于哪种形态：

- 单仓单应用：一个构建入口和一个主要运行单元。
- 单仓多模块：父构建或 workspace 统一管理多个模块。
- Monorepo：前后端、包、应用或基础设施共享版本和工具链。
- 多仓交付包：根目录本身不受 Git 管理，子目录分别是独立仓库。
- 源码与制品混合：源码旁包含 Jar、镜像脚本、压缩包、静态资源或第三方工程。
- 插件式拼装：框架、主应用、插件或扩展包需要复制、链接或安装后才能运行。

边界结论至少记录项目根、仓库数量、主版本线、主要入口、排除目录和无法验证的外部依赖。

## 事实源优先级

发生冲突时按以下优先级判断，并在报告中保留冲突本身：

1. 当前源码、构建清单、锁文件、DDL、迁移、容器和编排文件。
2. 运行配置、路由、服务发现、环境示例、CI 和发布脚本。
3. 测试、启动类、命令入口、前端路由和 API 客户端。
4. 当前维护的 README、AGENTS、架构、部署和运维文档。
5. 目录名、注释、历史脚本和文件时间只能作为线索。

## 分层扫描

### 交付与版本

检查 Git 根、子模块、分支或 tag 线索、版本号、锁文件、父构建、workspace、内部包引用和本地路径依赖。重点发现：

- 同一交付包中存在多个产品版本。
- 脚本、镜像标签、Jar 名称与源码版本不一致。
- 父构建声明了当前不存在的模块。
- 前端 workspace 或后端聚合构建依赖外部未交付目录。

### 功能与用户入口

从前端路由、页面、菜单初始化数据、控制器/API、CLI、任务入口和移动端页面归纳能力域。模块边界优先依据：

- 独立用户目标或角色入口。
- API 前缀、服务边界或可独立部署单元。
- 独立数据所有权、状态机或权限范围。
- 可复用平台能力，例如认证、文件、消息、调度、配置和审计。

目录只是实现载体。同一能力跨多个仓库时合并解释；同一目录包含多个独立能力时拆开说明。

### 构建与运行

识别语言、框架、运行时、包管理器、版本约束、构建 profile、启动类和环境变量。至少回答：

- 什么必须先构建，什么可以并行构建。
- 哪些产物被其他模块直接依赖。
- 最小可运行链路需要哪些服务。
- 哪些命令在当前环境经过验证，哪些只来自文档或脚本。

### 部署与基础设施

检查 Dockerfile、Compose、Kubernetes、Helm、Nginx、systemd、CI/CD、云部署描述和发布脚本。结合配置还原：

- 客户端、反向代理、网关、服务、任务、数据和中间件关系。
- 服务发现、配置中心、密钥注入、持久卷和静态资源位置。
- 健康检查、日志、指标、追踪、告警、备份和恢复入口。

不要把本地开发端口直接当作生产端口，也不要把存在 Dockerfile 等同于存在完整部署编排。

### 数据与集成

检查 DDL、迁移、种子数据、ORM 模型、数据源配置、缓存键、消息主题、对象存储和第三方 API。分别记录：

- 数据库或 schema 的职责和消费者。
- 初始化与升级顺序。
- 事务、租户、数据权限和主数据边界。
- 外部系统是必选、可选还是降级能力。

### 质量与运维

按业务风险判断测试和运维材料是否足够：

- 单元、集成、契约、端到端、冒烟和迁移测试分布。
- CI 是否实际调用这些验证。
- 日志、指标、链路、审计、健康检查和告警是否可用。
- 备份、恢复、回滚、容量和故障处理是否有事实支撑。

## 深挖触发条件

出现以下线索时继续追踪，直到能解释依赖方向或明确为待确认：

- 配置或路由引用了不存在的服务。
- 代码导入了未交付的内部包。
- 部署脚本复制不存在的目录或产物。
- 同一能力存在两个实现或两个运行入口。
- README、构建文件和源码版本互相冲突。
- 数据库脚本包含业务库、流程库、任务库等多个独立域。
- 前端需要手工拼装插件、子应用或静态资源。

扫描广度要覆盖完整交付边界，深度集中在主链路、冲突点、缺失线索和高风险依赖。
