# 项目接手分析

## 职责与边界

面向接手开发者或技术负责人，判断“交付了什么、能否构建运行、缺什么、先接手什么、怎样确认可维护”。报告是指定范围与时点的评估快照。

本文维护分析流程与操作边界；[项目发现](references/project-discovery.md) 维护调研方法，[证据判定](references/evidence-completeness-security.md) 维护完整性、安全和质量要求，[报告模板](assets/project-handover-report-template.md) 统一维护默认骨架与最低内容。

系统/部署架构及技术原理由 `project-module-architecture-doc-authoring` 维护，业务环节与字段、状态、权限明细由 `business-closed-loop-analysis` 维护，最小使用入口归 README。报告引用这些事实并评价接手影响，不复制整套正文；缺少专题时仍保留足以独立作出接手判断的上下文，不自动生成其他交付物。

## 输入与前置条件

确定项目或交付包、版本基线、可访问范围和报告目标，读取项目规则与已有报告。未限制范围时覆盖完整可访问项目，列出排除、不可读取及未验证部分。

区分新分析、局部更新与仅保存：保存保留原内容、有效修正及证据状态，不重跑调研；局部更新只复核受影响判断。重新评估既有报告须明确新基线，不因技术文档更新自动改写历史快照。

## 执行流程

1. **建立交付地图**：读取项目发现规则，识别根仓、子仓、主线/历史版本、插件和生成物。运行 `scripts/scan_project_handover.py <project-root> --format markdown` 获取候选清单，关键事实回查源码与配置。多个独立仓库可作为一个交付包分析。
2. **还原系统关系**：从业务能力到代码包、客户端、服务、存储、中间件和外部系统，解释实际运行单元及主链路。区分构建、运行、数据、配置、部署和可选集成依赖；多版本、多实现或拼装冲突必须给依据，不能凭名称推荐主线。
3. **评估完整性与风险**：读取证据判定规则，覆盖源码、构建、运行、部署、数据、测试、运维和文档。缺失须有预期证据及影响；未知与可选能力不能判为缺代码。每个关键判断记录状态、证据、影响、置信度和验证方法。
4. **形成接手报告**：完整读取报告模板，按判断与动作组织事实；深入主链路、冲突、缺失和高风险依赖，其他模块保留职责、入口、依赖及完整性状态。已有可靠专题摘要引用，过期或矛盾之处说明对判断的影响。
5. **复核与交付**：回查关键事实，按模板检查接手路径、图表、链接和未决事项，按证据规则检查敏感信息。仅在安全且成本合理、授权范围内执行构建或启动验证，明确记录未执行与失败。

## 核心约束

默认简体中文，代码、标识和既有术语保持原样，用户语言要求优先。源码和配置用于核实实现，权威文档用于核实交付约定与规范；冲突必须说明，不能把静态配置当生产状态，也不能用实现覆盖有效规范。

不读取依赖缓存、构建产物、压缩包或大体积二进制的内容，除非它们是唯一交付物且用户要求检查。不输出凭据或无必要的内网端点；不自动修代码、配置、数据库或部署环境，不因发现问题提交代码或操作外部系统。

## 产出边界与交付

默认一份完整项目级 Markdown 报告，采用报告模板的**默认骨架**，可按规模合并章节但保留适用判断与证据；用户要求摘要或专项范围时按其范围输出。

路径依次选择用户指定位置、项目已有同类报告、`agent-works/architecture/project-handover-report.md`。同一报告修订维护原文件；明确要求新快照时保留旧成果。交付前清除模板占位符和生成提示。

交付绝对路径、范围、主要结论、实际验证方式及结果、阻塞和交付方待答问题。接手动作是建议，不自动执行修复或生成未来需求、开发计划和运维手册。

## 验证与完成标准

- 项目全景、关键模块与依赖、八类完整性判断、风险证据、接手动作及交付方问题均有适用内容，不能缩成技术栈和风险摘要。
- 沿环境准备、装配/启动、代表性业务操作、结果检查和失败定位走读；读者能判断下一步与通过条件。不可执行的步骤标明所需材料和未验证限制，不以走读代替实测。
- 区分源码存在、可构建、可运行与可部署；区分仓库支持方案与实际环境。每个缺失结论满足预期证据、搜索范围和影响要求。
- 检查路径、命令、版本、端口、API、表、配置、依赖方向及 Mermaid；摘要不复制专题正文，报告内证据和行动相互可定位，未完成验证如实披露。
