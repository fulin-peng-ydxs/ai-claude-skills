# 项目接手报告默认模型

## 输出原则

默认生成一份完整、可独立阅读的项目级 Markdown 报告。章节顺序是稳定输出契约，用于保证不同项目的报告可比较，也保证结果与深度分析模式一致。

- 默认保留以下 14 个主章节，不把它们合并成泛化摘要。
- 项目不涉及某项时，在原章节中写明“不适用”、判断依据和是否需要交付方确认。
- 可以按项目事实新增二级或三级章节，但不要改变核心信息的归属。
- 用户明确要求精简版、专项版或其它结构时，才偏离默认骨架。
- 报告标题使用 `# {项目名} 项目代码接手报告`；能够确认产品类型时可加入类型，例如“低代码平台代码接手报告”。
- 文档应达到让新负责人无需先遍历源码，就能理解系统并制定接手动作的详细程度；不要人为限制篇幅。

## 默认章节骨架

### 1. 一页结论

用约 8 至 15 条高密度结论回答：

- 项目是什么，面向哪些用户、角色或业务目标。
- 当前交付是单仓、Monorepo、多仓交付包、插件拼装还是源码与制品混合。
- 主后端、主前端、移动端、独立服务和基础设施分别是什么。
- 代码是否基本完整，哪些模块明确缺失，哪些只是版本或交付范围待确认。
- 是否具备直接构建、运行和生产部署条件。
- 最关键的版本、安全、测试、部署和维护风险。
- 推荐的主版本、主入口和最小接手链路。

这部分必须能脱离后文单独阅读。不要写宣传语，也不要只重复技术栈。

### 2. 代码包全景地图

逐个解释根目录下真正有独立职责的仓库、应用、公共包、脚本和资源包。推荐表格：

| 目录或仓库 | 类型 | 核心职责 | 重要程度 | 组合或运行说明 |
| --- | --- | --- | --- | --- |

多仓项目必须说明：

- 根目录是否为 Git 仓库、各子仓库是否独立管理。
- 哪些属于主线源码、历史版本、第三方源码、静态资源、部署材料或生成物。
- 哪些仓库必须组合、复制、链接或先发布到本地制品库才能运行。

不要机械列出没有接手价值的所有文件夹。

### 3. 总体功能说明

至少包含：

#### 平台或产品定位

解释系统解决什么问题、主要使用者、核心业务边界和不负责的范围。

#### 核心能力地图

把业务和平台能力映射到主要代码入口：

| 能力域 | 功能说明 | 用户入口 | 主要代码或服务入口 |
| --- | --- | --- | --- |

#### 核心业务闭环

从用户动作开始，说明认证、权限、业务处理、数据落库、异步任务、消息或外部系统如何形成闭环。复杂项目使用 Mermaid `flowchart`；至少覆盖最核心的一条链路。

### 4. 总体技术架构

至少包含：

#### 运行时总览

使用 Mermaid 展示客户端、反向代理或网关、后端运行单元、独立服务、中间件、数据库、文件存储和外部系统。图中节点必须和后续模块、端口及依赖表一致。

#### 技术栈

后端、前端、移动端、数据、中间件和工程化工具分开说明。技术栈不能只列名称：

| 技术或框架 | 版本线索 | 在系统中的用途 | 证据入口 |
| --- | --- | --- | --- |

#### 代码分层与关键机制

说明项目真实采用的分层，例如 controller/service/repository、领域层、插件层、共享包、API 契约包、状态管理和页面路由。补充认证、权限、租户、事务、缓存、消息、调度、配置和错误处理等横切机制。

### 5. 部署架构

这一章不能被简化成“存在 Dockerfile”。应尽可能还原实际部署画像。

#### 核心运行单元和端口

| 运行单元 | 服务或应用名 | 端口或路径 | 入口配置 | 是否主链路必需 |
| --- | --- | --- | --- | --- |

把源码默认值、本地开发值、部署脚本值和已验证生产值区分开；生产值未知时明确标注。

#### 独立服务和中间件

说明注册中心、配置中心、缓存、消息队列、任务平台、报表、文件预览、搜索、可观测性等独立运行单元及依赖关系。

#### 编译与打包顺序

从父构建、内部依赖、workspace、本地包、发布脚本或 CI 中还原顺序。复杂关系使用 Mermaid `flowchart`，并说明哪些步骤可并行。

#### Docker、编排和发布材料

分别评估 Dockerfile、Compose、Kubernetes/Helm、Nginx、CI/CD、镜像标签、发布脚本、制品目录、健康检查、回滚和备份材料是否存在且版本一致。

#### 前端或客户端部署

说明各应用的构建产物、基础路径、反向代理、API 地址、WebSocket、静态资源和多应用路径约定。非 Web 项目在此说明 CLI、桌面端、SDK 或其它客户端的分发方式。

#### 配置装配和启动顺序

说明配置文件、配置中心、环境变量、密钥、数据库、静态资源和外部服务如何装配，并给出最小启动顺序。区分静态推断和已经执行验证的结果。

### 6. 模块职责与依赖关系

按业务模块、平台模块或独立运行单元逐项说明，不按文件夹机械拆分。每个关键模块至少写清：

- 模块定位和职责边界。
- 主要源码、启动、页面、API、配置和数据入口。
- 上游调用者、下游依赖和共享能力。
- 对主链路的重要程度和故障影响。
- 当前完整性状态及证据。

模块较多时，每个模块使用独立三级标题，保持“职责、关键入口、依赖、完整性”顺序一致。

### 7. 依赖关系详细说明

至少拆分以下依赖类型，不能用一张没有语义的总箭头图代替：

#### 编译依赖

解释父子构建、公共依赖、内部制品、workspace、插件和生成代码之间的依赖及打包顺序。

#### 运行依赖

使用 Mermaid 或矩阵说明网关、服务、任务、消息、缓存、数据库和外部系统的调用方向。

#### 服务通信边界

按项目实际说明 HTTP/REST、RPC、Feign、gRPC、Dubbo、GraphQL、消息主题、事件或本地调用。列出主要契约入口，不堆砌全部接口。

#### 数据库与存储依赖

说明数据库/schema、表前缀或领域、迁移和初始化脚本、共享数据库、缓存、对象存储和文件目录的归属与消费者。

#### 配置依赖

说明配置中心、环境变量、配置文件、路由、密钥和功能开关如何影响运行单元。

#### 外部集成

说明第三方 API、许可证、云服务或私有制品是主链路必需、可选还是可降级。

### 8. 前端应用结构

Web、移动端、桌面端、CLI 或 SDK 按实际情况说明。章节标题默认保持“前端应用结构”，无前端时在本章说明客户端或对外消费方式：

- 应用、框架底座、组件库、插件和子应用的组合关系。
- 页面或命令域及其职责。
- 路由、状态管理、权限、API 客户端和构建入口。
- 多版本、重复应用、手工拼装和基础路径风险。

有三个以上组成单元时使用 Mermaid 关系图。纯后端服务或纯库项目保留本章并说明“不适用”及对外消费方式。

### 9. 模块完整性评估

至少拆成以下四组：

#### 基本完整的核心模块

只列有明确源码、构建、入口和必要配置证据的模块，并说明“完整”具体指源码、构建还是已运行验证。

#### 缺失或待确认的模块

| 模块或线索 | 预期证据 | 当前现状 | 影响 | 结论 | 置信度 |
| --- | --- | --- | --- | --- | --- |

“缺失”和“待确认”严格使用证据门禁，不把可选产品能力误判为缺代码。

#### 版本、脚本和配置冲突

比较源码版本、构建版本、锁文件、镜像标签、发布脚本、文档和配置导出中的版本线索。

#### 测试、质量与可运维性

说明单元、集成、契约、端到端和冒烟测试的真实覆盖；同时评估健康检查、日志、指标、追踪、告警、备份、恢复和回滚。

最后增加项目级完整性矩阵：

| 维度 | 状态 | 关键证据 | 主要影响 | 置信度 | 下一步验证 |
| --- | --- | --- | --- | --- | --- |
| 源码 |  |  |  |  |  |
| 构建 |  |  |  |  |  |
| 运行 |  |  |  |  |  |
| 部署 |  |  |  |  |  |
| 数据 |  |  |  |  |  |
| 测试 |  |  |  |  |  |
| 运维 |  |  |  |  |  |
| 文档 |  |  |  |  |  |

### 10. 典型调用链

选择最能帮助接手的真实链路，而不是只画技术组件：

- 登录、身份建立、菜单或权限加载。
- 核心业务新增、查询、审批或状态推进。
- 文件、消息、任务、报表、支付或外部集成链路。
- 失败恢复、异步回调或补偿链路。

复杂项目默认提供 2 至 4 张 Mermaid `sequenceDiagram`。每条链路必须能回查到页面、API、服务、数据或消息证据；无法确认的步骤标注为静态推断。

### 11. 接手路线图

默认沿用“先确认边界、再跑通最小主链路、再补齐业务模块、最后工程治理”的节奏。可按项目复杂度使用日期或阶段标题，但必须包含：

| 阶段 | 关键任务 | 前置条件 | 通过标准 | 产出物 |
| --- | --- | --- | --- | --- |

- 第一阶段：确认交付范围、主版本、许可证、外部依赖和敏感配置。
- 第二阶段：准备数据和中间件，按顺序启动最小服务集，跑通主入口。
- 第三阶段：逐项验证核心业务、文件、消息、任务、报表、客户端等模块。
- 第四阶段：统一版本和部署、补测试、监控、备份、回滚及团队规范。

不要承诺没有依据的工期；使用“第一天、第一周”等表达时，将其标注为建议节奏。

### 12. 接手时最该问交付方的问题

问题必须来自代码冲突或无法静态确认的事实，并且答案会改变模块范围、部署方案、安全策略或接手顺序。优先覆盖：

- 正式版本和完整交付清单。
- 可选、付费、许可证或私有模块。
- 多实现、多前端、多流程或多报表方案的生产主线。
- 生产配置、数据库升级、部署、备份和恢复材料。
- 历史二开、补丁分支、未合并代码和外部私有制品。

通常保留 8 至 15 个高价值问题，不把可从代码自行确认的细节转嫁给交付方。

### 13. 关键证据入口

用表格列出足以复核报告核心结论的文件：

| 证据用途 | 相对路径 | 支持的结论 |
| --- | --- | --- |

至少覆盖主构建、主要 README、启动入口、路由、配置、数据库、部署、中间件、前端和测试。只使用项目相对路径，不输出本机用户目录。

### 14. 最后建议

用一段综合判断说明项目真正的接手难点，再给出团队应建立的标准运行画像：

| 标准项 | 建议落地 |
| --- | --- |
| 主版本和工具链 |  |
| 主服务及客户端入口 |  |
| 配置与密钥管理 |  |
| 数据初始化与升级 |  |
| 部署和回滚 |  |
| 验证与测试 |  |
| 监控、备份和恢复 |  |
| 文档索引和维护责任 |  |

最后结论必须回答“这个项目能否接手、当前最先做什么、完成什么才算进入可维护状态”，不重复前文清单。

## 表达和深度门禁

- 先写功能和接手结论，再写技术细节；不要从依赖清单开始。
- 模块、端口、技术栈、依赖、完整性和风险分别用适合的表格，不把所有信息塞进一张总表。
- 多仓、多服务、多数据库或插件拼装项目至少提供三类图：总体运行图、依赖或拼装图、核心调用时序图。
- 所有图和表必须有正文解释，不能只贴图。
- 每个关键判断尽量带相对路径、类、函数、配置键、API、表或命令证据。
- 报告可以很长，但避免复制 README、完整配置、全部 API 或全部源码目录。
- 已执行验证、静态确认、文档声明和待确认问题必须明确区分。
