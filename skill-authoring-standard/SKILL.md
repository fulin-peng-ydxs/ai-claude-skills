# 技能编写规范

## 职责与边界

本文维护自有技能的设计流程、资源组织、产物契约接入和技能重构核查；[命名规范](references/skill-naming.md) 维护名称及重命名契约，[正文骨架](references/skill-template.md) 唯一维护技能正文的六个主题及章内组织规则。

技能文件、初始化和基础校验复用 [skill-creator](../skill-creator/SKILL.md)，不修改系统技能或复制其教程。通用文档规则由下述全局规范维护，具体业务规则与产物要求由目标技能维护；从参考产物创建可复用模板技能由 `template-creator` 承接。不自动修改全局路由、同步其他工具、提交 Git 或迁移无关技能。

## 输入与前置条件

确定目标技能、操作类型及授权范围；读取实际基线（含未提交改动）、相邻技能和消费方，判断应新增、扩展还是保持分工。比较实际输出契约，不能只凭名称或描述判断无重叠。只追问无法核实且影响职责或正确性的信息。

开始设计或审查前读取 [文档结构与输出规范](~/ai-agent-config/config/force/document-output.md) 和 [文档边界规范](~/ai-agent-config/config/force/document-boundaries.md)；本技能不重新定义其中的结构策略、裁剪、内容保留或权威维护规则。局部修改只应用受影响要求。

## 执行流程

1. **锁定基线**：识别新建、整体重构或局部修改。重构先按下述语义保留审查提取契约；局部修改仅提取受影响契约及关联约束，新建以用户要求和有效规范为依据。
2. **确定入口**：创建或重命名时读取命名规范，核对标识冲突及相邻职责。用简洁的 `description` 表达能力和触发场景，仅为容易误触发的任务补排除条件。
3. **先设计产物，再设计执行**：用代表性请求确定实际交付类型；生成文档的技能先完成下述模板设计及试填，再设计取证、分析和填充步骤。新建及整体重构使用正文模板；前提与授权早于动作，执行分支能定位结果与失败出口。
4. **组织资源**：按下述资源选择规则落地；需要初始化时使用 `skill-creator` 的 `scripts/init_skill.py`。操作脚本按系统技能的复用与确定性收益标准选择；检查器新增及扩展统一按协作规则“做测试时”的门槛判断。
5. **验证交付**：完成适用的语义对照、场景核查和机器验证；发现问题先修复再复核。按实际证据报告完成范围及限制。

## 核心约束

- 调用标识、中文标题和 UI 名称按命名规范维护；局部修改不自动改名。获准重命名时处理引用与对应副本，不留下两个可发现的同职责入口。
- 技能正文与生成的产物分别设计；正文骨架不能充当业务文档模板。创建时的设计检查不复制成目标技能每次执行的额外流程，目标技能只保留运行时实际需要的判断与检查。
- 自有约定只补充系统技能和全局规则未定义的内容。执行入口须能判断做什么、何时读取资源、何时停止，不能退化为链接目录。
- 技能作为执行说明设计，具体要求遵循全局文档规范的“工程类文档的执行要求”。配置或规则须给出可直接消费的格式；稳定重复的机器判定优先交给小型脚本。技能的编写/审查要求不复制成用户每次执行任务的审批清单。

**生成文档技能的设计要求**

1. **确定产物**：列出实际交付类型、读者任务和范围，不混入相邻技能产物。先按文档边界规范核对权威位置及章节分工，再按文档输出规范的“适用分支”确定结构与检查要求；正式模板继续消费“固定生成原则”“输出契约的最低定义”和“面向读者的内容验收”。目标技能与模板只落实本地产物的分工和专项内容要求，不重新定义通用规则。
2. **完成唯一模板**：优先维护已有产物资源，文件名不强制迁移。将散落在技能正文和其他契约中的产物格式及内容要求迁入该模板；共享业务语义保持原权威入口并引用，取证方法留在专项参考。不保留第二份完整目录或字段定义。
3. **试填后接流程**：按全局文档校验规则选择适用场景试填模板。必须能在声明的结构范围内表达完整事实和分析，不靠越出槽位新增结构才能完成；只给目录、主题清单或“按需输出”不算完成。
4. **建立消费路径**：技能的生成/整体重构分支明确何时读取哪个完整模板，更新和审查分支读取受影响的内容要求，保存分支保留基线；关键要求不能藏在可选资源。普通对话、操作技能、提交消息和机器数据不额外套报告。
5. **接入检查**：固定 Markdown 骨架使用下方共用检查器，其他确定格式复用已有工具。模板与检查器保持同源，验证合法产物及缺字段、错序、非法新增等反例；没有模板或未完成试填，不宣称文档技能创建完成。

**模板与检查入口**

模板和命名检查器复用 `ai-constraint-doc-authoring/scripts/document_markdown.py`；前者从权威资源的 `document-template` 代码块读取结构，后者从命名规范读取词表。模板语法、支持范围与精确命令见 [检查器用法](references/template-validation.md)，不另建 schema 或格式注册表。跨技能使用时须同级安装本技能及上述解析器依赖，缺失明确报错。

**通用文档规范的引用位置**

按实际执行分支建立读取路径，同一路径已读取的规范直接复用；不要求每份文件放相同链接。

- 独立产物模板且没有共用执行契约：由唯一模板接入通用文档规范；技能入口只说明何时读取模板、交付范围和关键限制，不再为同一产物重复直引这些规范。
- 多技能共用执行契约：由共用契约接入通用文档规范；技能在适用分支读取共用契约，阶段模板引用该共用入口并维护本阶段固定格式，不再建立平行的通用规范接入口。
- 编写、重构或审查技能本身：使用本技能前置条件中的全局规范作为设计依据；这是独立的设计分支，不因产物模板另有引用而删除。
- 正式文档原有内联产物要求迁入其唯一模板；对话反馈、嵌入片段及机器数据沿用其专用契约，不为统一接入位置新增完整报告。

引用写明用途与读取条件，关键门禁不能只藏在可选资源中；保存和局部更新沿用授权基线，不因“生成前读取”重套完整模板。设计检查不复制成目标技能每次执行的审批清单。

**正文与独立资源的选择**

- `SKILL.md`：职责、模式、共用流程、授权与停止、交付及完成判断；短小且总要一起理解的专项说明就地维护。
- 独立参考或模板：有独立读取场景、维护职责或共享收益，入口明确读取时机；完整产物模板在该处维护。
- 既有权威入口：已有全局规则、相邻技能或共用契约直接消费，只补本地差异。

总是共同读取和修改、又无独立维护或共享收益的文件优先整合；拆分须有大于跳转成本的收益。不按字数或文件数机械拆合，不拆散完整判断链。

## 产出边界与交付

在用户指定位置交付有效 `SKILL.md` 及实际需要的资源；未指定时沿用 `skill-creator` 的用户目录约定。不附加无用途的 README、变更日志或空目录。说明调用名称、职责、实质变化与验证结果；文件创建不等于自动发现、默认路由或跨工具同步已经验证。

## 验证与完成标准

- 运行 `skill-creator` 目录下的 `scripts/quick_validate.py <目标技能目录>`。名称、标题或 UI 元数据变化时，另运行本技能的 `scripts/validate_skill_names.py <目标目录>`；修改命名检查器时运行 `python3 -m unittest discover -s tests -p 'test_*.py'`（工作目录为本技能目录）。
- 核对变更引用、锚点、资源读取条件及 UI 元数据；按实际顺序检查依赖和门禁。新增或修改脚本执行适用验证。
- 用实际或代表性输入完成一次输入到结果的查用：每个分支能定位下一动作、所需授权和失败出口；只有分类说明、空模板或反复提示“另行确认”，但缺少可执行内容时不通过。脚本验证与场景走读分别报告。
- 创建或调整模板时，先按 [文档边界规范](~/ai-agent-config/config/force/document-boundaries.md) 核对模板资源的归属、章节分工与声明，再运行共用检查器的 `--check-template`，按文档输出规范完成代表性试填、内容与证据核对及正反例验证；试填产物的边界仍按同一边界规范核对，并检查上述引用路径。将检查入口接入目标技能。正文自身按正文模板校验固定主题及章内内容有效性；局部修改不借此重写未授权结构。
- 生成文档技能在全局代表性场景中，对照具体内容判据及基线，检查有完整正文、未知未被裁掉、无越界补写或重复定义；另用仅列标题或误裁未知条件的反例确认判据能拒绝缺项，不只检查目录齐全。
- 组合模板沿实际引用展开，检查标题层级、字段和引用无重复、错位、遗漏或提示残留。技能重构按下述语义保留审查逐项对照；相邻场景核查不得误触发其他产物或外部写入，无输入或异常路径按目标技能实际能力选择。
- 按全局文档校验规则区分格式、语义及实际行为证据；场景走读不称为独立运行验证，单次产物检查不宣称多次生成稳定性已经证实。只报告实际完成的检查。

**重构的语义保留审查**

本节只维护技能重构的契约对照方法；审查材料在执行中形成，不默认另建报告，也不复制到目标业务技能。

1. **提取契约**：读取基线正文、相关资源、脚本和元数据，提取触发与排除、输入、执行分支、授权与停止、输出保存、异常、验证和资源依赖。记录条件、强度、例外、固定字段及来源，不把原有冲突自动当成有效要求。
2. **定位去向**：逐项对应原位保留、合并、迁移或有依据的修改/删除。合并保留条件和例外，迁移须在适用执行分支实际可达，不能只验证链接存在。
3. **核实变化**：变化依据须来自用户要求、有效规范、已核实事实或明确的权威承载位置；无依据的遗漏先恢复。反查新增内容是否扩大触发、权限、交付物或验证负担，实质歧义说明影响并保留待决状态。
4. **比较场景**：比较正常、相邻误触发、缺失输入及适用异常的前后行为；声明行为不变时核对结果一致，契约变化核对其依据。保存、仅审查和授权操作不得误触发生成、修复或外部写入；机器契约变化执行适用测试。
5. **判定结果**：所有适用契约均有可定位去向或有效变化依据，发现的问题已修复并复核，才可报告语义保留检查通过；说明实质变化、证据与未验证项。一般重构不强制子代理，自审不称为独立审查。
