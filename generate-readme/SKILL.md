# Generate README

这个技能只负责一件事：

- 基于当前项目真实文件生成或更新项目根目录 `README.md`

## 核心原则

1. 固定的是分析流程，不是 README 章节。
2. README 必须中文输出，内容要服务于人类读者快速理解项目和快速上手。
3. 只写能从仓库文件、配置、脚本、现有文档或实际验证结果确认的信息。
4. 对不能确认的信息不要补全成结论，改为写入“待确认”或在最终回复中说明未写入原因。
5. 已有 README 优先增量更新，保留仍然有效的人工说明，避免无依据的大面积重写。

## 执行流程

1. 识别项目根目录和现有 README 状态。
2. 扫描项目类型、技术栈、入口、构建配置、运行配置、测试配置和部署线索。
3. 提炼事实并分级：已确认、实测通过、未验证、待确认。
4. 根据项目类型选择 README 结构，不套用固定章节。
5. 新建或更新 `README.md`。
6. 能验证的命令尽量验证；不能验证时明确说明未运行或失败原因。
7. 最终回复说明扫描范围、写入方式、主要变化和验证情况。

## 优先扫描清单

根据项目实际存在的文件选择扫描，不要求所有项目都具备：

1. 项目说明：`README.md`、`AGENTS.md`、`.claude/CLAUDE.md`、`docs/`。
2. 前端项目：`package.json`、`pnpm-lock.yaml`、`package-lock.json`、`yarn.lock`、`vite.config.*`、`next.config.*`、`src/`、`public/`。
3. Java 项目：`pom.xml`、`build.gradle`、`settings.gradle`、`src/main`、`src/test`、`application*.yml`、`application*.properties`。
4. Python 项目：`pyproject.toml`、`requirements*.txt`、`setup.py`、`src/`、`tests/`。
5. Go/Rust 等项目：`go.mod`、`Cargo.toml`、源码入口和测试目录。
6. 脚本或工具项目：`scripts/`、可执行文件、示例输入输出、配置样例。
7. 部署和环境：`Dockerfile`、`docker-compose*.yml`、`.github/workflows/`、`.gitlab-ci.yml`、`.env.example`、`Makefile`。

优先使用 `rg --files`、`find`、`sed`、`git status` 等轻量命令读取上下文。读取配置时只提取 README 需要的信息，避免把无关细节写进文档。

## README 结构选择

不要强制所有项目使用同一套章节。根据项目类型选择必要章节：

1. 通用项目通常包含：项目简介、技术栈、环境要求、快速开始、常用命令、配置说明。
2. 服务端项目可补充：服务架构、接口或模块说明、数据库或中间件依赖、部署说明。
3. 前端项目可补充：页面或功能概览、开发预览、构建产物、环境变量。
4. 库或 SDK 项目可补充：安装方式、基础用法、API 示例、版本兼容。
5. 脚本或 CLI 项目可补充：命令用法、参数说明、示例、输出说明。
6. 技能或插件项目可补充：触发场景、目录结构、安装位置、使用方式、维护约束。

如果某一章节没有可靠事实支撑，不要为了完整而硬写。

## 事实和验证规则

1. 命令必须来自真实配置文件、脚本、Makefile、README 或实际目录结构。
2. 运行、构建、测试命令如果已执行成功，可写成已验证。
3. 未执行的命令可以写入 README，但不要声称已验证。
4. 执行失败的命令不要包装成可用步骤；应在最终回复中说明失败原因，必要时在 README 中写成注意事项。
5. 环境变量只写 `.env.example`、配置文件或文档中能确认的项。
6. 业务用途不能只根据仓库名猜测；缺少证据时使用保守描述。

## 更新已有 README

1. 先判断现有 README 哪些内容仍然有效。
2. 保留有效的人写说明、业务背景、注意事项和已有链接。
3. 修正过期命令、错误依赖、失效目录和不一致描述。
4. 补齐缺失的快速开始、常用命令、配置说明和验证信息。
5. 不要删除无法判断真假的内容；可移动到“待确认”或在最终回复中提示用户确认。
6. 避免无必要的全量重写，除非现有 README 基本为空、明显模板化或与项目事实严重不符。

## 执行约束

1. README 内容必须输出中文。
2. 不要照抄 `AGENTS.md` 或 `.claude/CLAUDE.md`，但基础事实必须一致。
3. 不要为了补 README 而改动无关文件。
4. 不要编造部署环境、账号权限、服务地址、数据库信息、接口地址或发布流程。
5. 不要把内部执行过程写成 README 正文；README 面向项目使用者，不是生成日志。
6. 若用户只要求评估或建议，不要擅自修改 README。

## 输出要求

最终回复至少说明：

1. 扫描了哪些关键文件或目录。
2. `README.md` 是新建、增量更新还是重写。
3. 本次主要补充或修正了哪些内容。
4. 哪些命令或检查已经验证，哪些未验证。
5. 是否存在需要用户确认的信息。
