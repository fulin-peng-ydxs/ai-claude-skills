# 前端审查清单

本文维护生成前的依据核对、缺口识别和任务能力覆盖；先按 [技能正文的模式与输入](../SKILL.md#职责与模式) 确定本次范围的模式，再读取对应检查项。授权、确认及状态规则由正文维护，以下清单不另行设定生成门槛。

## 事实归纳的依据检查

- 已定位本次相关页面、组件、样式入口及 token 来源。
- 已阅读足以代表本次规则的页面或组件；涉及高密度界面时覆盖其代表性样本。
- 能区分稳定规律、合理角色差异与实现缺陷，并对照有效规范判断冲突。
- 能从有效契约、代表性实现或已确认需求确定本次目标视口、输入方式及布局边界；未知项说明缺口，不从框架或可安装能力推断设备范围。
- 引用的路径、组件和命令真实存在；样本不足时缩小结论范围，不假称覆盖全项目。

局部规范更新只需与本次变更相关的依据；不因页面少或缺少某类组件否定可归纳的规则。

## 初始化的输入检查

- 产品核心任务、首批页面或工作流及目标用户足以支撑设计选择。
- 目标设备与输入方式明确，安装、离线或触摸等能力按实际需求判断。
- 已识别有效品牌规范、原型、参考设计和已选组件库；没有这些材料本身不阻塞初始化。
- 必要设计决策已由用户指定、确认或授权 AI 作出；未知技术栈、非关键数值或次要能力可保留缺口，不编造实现。
- 拟写入规则能支撑首批代表性任务，计划组件与真实组件可区分，验收判据不依赖尚不存在的命令。

无代码时不要求现成组件、样式入口或渲染证据。缺少核心任务或目标设备时先补信息；用户只要候选方案或草稿时保留待确认状态，不生成冒充已生效规则的文档。

## 决策缺口与冲突

以下信号用于识别需要分析的缺口；不自动触发确认。先形成推荐方案，已有明确授权覆盖时直接执行，只确认尚未授权的关键选择。多个风格或实现并存只有在同角色规则冲突时才构成收敛问题。初始化缺少 token 或现成组件不是缺陷。

- 同类组件出现多套互相冲突的视觉实现
- 同一项目同时存在两种以上明显不同的风格体系
- 样式大量内联、零散、复制粘贴，难以抽象成稳定 token
- 几乎没有主题变量，颜色和尺寸定义到处散落
- 当前证据无法支持用户要求的规范范围，且需要决定是否扩大目标
- 需要在用户尚未授权的多个设计方向之间选择
- 已有 `DESIGN.md`，且新归纳结果会改变已有关键规范
- 高密度界面的空间、滚动或容器选择造成可观察的使用障碍，且收敛方案需要改变尚未授权的关键规范
- 主色、字体、圆角、间距或阴影体系存在多套冲突方案
- 页面风格明显不统一，无法判断应以哪部分为主
- 项目缺少关键规范，无法完整定义组件或布局规则
- 需要在多个候选方向之间做产品级选择，例如“保留旧后台风格”还是“收敛为新的统一风格”

## 建议补齐项

发现缺口时，可优先建议补齐：

- 颜色、字体、间距、圆角
- 基础组件规则：按钮、输入框、卡片、表格、弹窗、导航
- 响应式断点、容器宽度、页面留白
- 高密度界面规则：表格/列表空间利用、滚动层级、列宽分配、长文本处理、弹窗/抽屉/独立页面使用边界

高密度界面场景下，建议补齐项至少要落到可执行粒度：

- 列类型策略：哪些列窄、哪些列宽、哪些列固定、哪些列优先展示
- 长字段策略：省略、tooltip、两行截断、详情弹窗、展开行各在什么场景使用
- 操作列策略：可见动作数量、分组方式、是否固定及固定位置
- 滚动策略：页面滚动、表格滚动、弹窗正文滚动各自的边界
- 承载策略：普通 modal、宽 modal、drawer、全屏弹窗、独立页面的选择条件
- 桌面降级策略：在项目支持的最窄、典型和较宽视口下，哪些字段保留、截断、折叠或移入详情；不规定通用像素值

## 何时属于规范补齐

已有实现出现以下问题时，先检查有效契约是否已覆盖：已有明确规则则报告实现偏差，不靠改规范解决；只有契约缺失或经确认需要调整时才补齐规范：

- 固定小高度表格容器影响主内容区使用
- 页面、表格、弹窗或抽屉的滚动互相争抢，造成内容或操作不可达
- 列宽分配粗糙，关键字段难以判读
- 长文本处理方式导致行高失控或信息难以扫描
- 弹窗承载复杂表格、批量操作或长链路录入，导致必要信息或操作不可达

进入“规范补齐”后，必须：

- 明确指出当前实现中不宜直接固化为规范的部分
- 给出拟补齐的规范项
- 未获授权的关键选择确认后再写入；已有授权不重复确认

## 任务与能力规范覆盖

读取项目已确认规则；已有实现时结合代表性样本，初始化时结合首批需求与设计方案，按本次范围选择以下能力。通用任务适用于桌面和移动端，原生输入、触摸与安装/缓存仅在项目使用时覆盖。缺口先区分局部记录项与尚需确认的产品决策。

| 方向 | 应能从规范中回答的问题 |
|---|---|
| 任务与组件状态 | 加载、空、错误、无权限、提交中与成功反馈等适用任务状态如何呈现、转换和恢复？组件的默认、悬停、按下、展开、选中、聚焦与禁用状态如何区分？按角色和支持的输入方式选择，不要求每个组件具备所有状态。 |
| 焦点与状态承接 | 复合控件由谁承接强调，原生选择结束后如何保留有效焦点？弹层初始及返回焦点如何选择，交接到新任务后如何避免抢回？视觉与行为各复用哪个入口，不要求同一焦点样式或默认目标。 |
| 弹层与辅助任务 | 支持哪些退出路径，各影响哪个任务与未保存内容？子流程取消如何返回有效父任务，提交中及对象失效时如何处理？消息与恢复动作在当前层是否可达？不默认规定外部关闭或保留所有父层。 |
| 顺序调整（涉及时） | 使用哪种操作入口和允许范围？预览与已保存顺序如何区分，取消、失败及替代输入路径如何承接？领域限制引用业务契约，不在 DESIGN 定义排序算法。 |
| 固定与滚动 | 页头、筛选、正文、操作栏、导航和弹层分别归谁滚动？哪些区域需要固定，哪些自然滚动？顶部/末端缓冲与整页越界如何区分？ |
| 可用空间与占位 | 固定操作与导航如何预留空间？最后一项可达、短内容无异常空白的判据是什么？涉及安全区和软键盘时如何适配？ |
| 控件与说明对齐 | 外框、文字内边距、帮助/错误文本、垂直中心各遵循哪种角色规则？原生日期/时间如何验证？数字编辑与列表比较是否各有明确约定？ |
| 密度与响应式 | 数据范围条件与展示工具如何区分？固定区占用后正文如何保持可用？长值、多条件和错误状态如何降级？浮层如何适配真实裁切、滚动能力与内容变化？如何减少视觉体量同时保留操作目标？ |
| 图表与瞬态提示 | 支持的输入方式各用什么读数入口？滚动、选择与下钻如何区分？离开或数据变化时哪些提示关闭、哪些选择保留？ |
| 用户文案与恢复 | 同类搜索与动作是否有统一名称？按钮、就近帮助、执行前确认与结果反馈各承接什么信息？局部备份失败与正式操作失败如何区分？用户能理解结果并找到下一步吗？ |
| 共享能力 | 同类行为第二次出现时如何选择组件、状态 helper 或样式入口？已有与新增消费点如何共同接入，未抽取如何说明？ |
| 数字与导航恢复 | 展示精度、编辑中间态及语义色各以什么规则为准？首次进入、缓存返回、下钻返回和刷新分别恢复什么状态？来源标记、筛选与返回入口的结束条件各是什么，记忆地址如何承接？ |
| 触摸与原生输入（涉及时） | 手势与替代入口、原生控件、软键盘往返和焦点交接的预期行为是什么？ |
| 安装与缓存（涉及时） | 安装态导航、离线、更新与恢复采用什么契约？ |
| 验证与事实源 | 关键规则是否有实现入口、适用状态和可观察判据？项目特有复测要求引用哪个入口？ |

尺寸、对齐方向、显隐时序、固定布局和图表策略只记录有效事实或已确认/授权范围内的选择；待确认提案单独标识。实现机制与复测操作分别引用对应架构或验证入口，不在 DESIGN 再建第二份流程。

## 输出前检查

若本次 `DESIGN.md` 包含高密度界面规范，生成前至少确认：

- 已写明主数据区空间利用和滚动层级
- 已写明列类型策略和长字段处理方式
- 已写明操作列和动作承载方式
- 已写明弹窗 / 抽屉 / 独立页边界
- 已写明项目支持视口下的降级策略

按上表复核本次适用契约：已有实现定位真实入口；初始化说明必要角色、拟建能力与可观察验收判据，不要求已有文件。状态按 SKILL.md 的决策、实现和证据维度分别表达；缺口与不适用项说明边界。实际证据使用 [前端验证规范](~/ai-agent-config/config/force/frontend-verification.md)，纸面走读不能证明界面已通过验收。

## 输出判断

- 归纳依据充分或初始化输入足够，且关键选择已有授权：写入本次适用规范。
- 存在不影响主规则的局部缺口：先交付确定部分，在缺口说明中标注剩余事项。
- 关键选择尚未授权或有效契约冲突：给具体推荐方案和影响，完成必要确认后写入；已有授权不重复索取。
- 核心任务或目标设备等关键信息不足：补足必要信息，继续可独立完成的工作；不因缺少代码要求先开发页面。
- 用户明确只要求提案或草稿：保持待确认状态，说明哪些内容尚不能用作开发硬约束。
