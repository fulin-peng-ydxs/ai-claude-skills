# 项目设计规范编写

## 职责与边界

将项目的界面决策沉淀为可指导后续开发的 `DESIGN.md`。默认输出到目标项目根目录，用户指定其他路径时遵循指定路径。

本文维护初始化与事实归纳流程、状态和授权边界；[输出契约与模板](references/design-md-template.md) 维护产物组织、token 承载和填写要求，[条件清单](references/frontend-audit-checklist.md) 维护依据核对与任务能力覆盖，实际设计契约归目标项目 DESIGN。

### 职责与模式

- **已有项目：事实归纳或修订。** 读取有效规范和代表性实现，提炼稳定规则，识别偏差与规范缺口；不把实现缺陷固化为规范。
- **从零项目：规范初始化。** 没有可分析的前端代码时，使用产品需求、目标用户与设备、品牌资料、设计稿及已确认决策建立可实施的初版。没有代码不构成阻塞。
- 按本次模块或规则选择模式，不只按仓库是否为空判断。只有后端或脚手架的项目可初始化；已有项目的新模块沿用共享契约，只初始化新增部分。
- 已有 DESIGN 但没有代码时，以已有契约为基准，只补本次范围，不重新发明设计系统。

本技能只编写规范。需要新的视觉或交互方案时配合 `frontend-design`，已有明确方案时直接承接；方案探索本身不授权开发页面或创建原型。只审核现有规范使用 `design-compliance-audit`，体验审核使用 `frontend-ux-audit`。不因规范存在待实现项而自动改代码。

## 输入与前置条件

### 已有项目：收集与归纳

- 定位页面、组件、布局、样式和主题入口，以及项目采用的 token 或组件库事实源。优先查看实际技术栈文件，如 HTML、JSX/TSX、Vue、CSS/SCSS、主题配置；不把扩展名列表当作支持范围限制。
- 默认不深挖后端、数据库、接口或无关脚本；仅当其直接决定本次前端文案、状态、配置或主题时，追踪必要依据，不扩展为业务或后端审核。
- 先定位本次范围内候选实现，再阅读足以代表页面类型和角色差异的样本。范围涉及高密度列表或表单时包含对应样本，不为局部规范更新强制全站扫描。
- 提炼颜色语义、字体层级、间距、圆角、组件状态、布局与滚动、适用视口及交互反馈。具体契约覆盖项只在参考清单维护。
- 不一致时区分合理角色差异、实现违规、规范过时与尚需决定的方向。提出收敛方案，不因某种写法出现较多就默认其正确。
- 已有 token 文件只引用来源和用途，不再抄一套数值。引用组件、路径和命令必须核实其存在。

### 从零项目：输入与初始化

先利用用户已提供的材料，补充询问只针对真正影响方案的缺口：

- 产品核心任务、目标受众和首批页面或工作流。
- 目标设备、输入方式与支持范围；桌面、移动、安装或离线能力分别判断。
- 已有品牌、参考设计、原型、组件库或技术约束；参考对象是启发还是必须遵守的契约须分清。
- 已确认的视觉方向和交互选择，以及用户交由 AI 决定的范围。

无需所有输入都完整才能推进：采用既有品牌和已确认方案，或在授权范围内配合 `frontend-design` 提出最小方案。核心任务或目标设备等影响方案的关键信息无法从材料确定时，先补足必要信息；可先给候选方向，但不凭空生成一套生效规范。

初版只覆盖首批真实需求：设计方向、基础 token 及语义、必要组件角色与状态、代表性页面结构、导航和反馈、支持视口及验收判据。未选技术栈时使用角色与行为描述，不发明实际文件路径、组件 API 或验证命令。计划中的组件和接入位置明确标为拟建。

没有 token 实现时，已确认的初始值可由 DESIGN 暂作事实源；后续实现采用独立 token 文件后，将数值权威来源迁移到该入口并更新引用，避免两处并行维护。只编写规范时不代为创建 token 代码。

## 执行流程

1. **定位目标与授权。** 确定项目目录、文档路径及本次范围；读取适用项目规则和已有 DESIGN。目标路径无法确定时只澄清必要信息，不把规范写入技能仓库或任意当前目录。
2. **选择模式与依据。** 按下文收集事实归纳或初始化所需材料；用户要求、有效契约与已授权选择优先，代码现状不能自动覆盖规范。
3. **检查适用内容。** 首次生成或整体重构读取 [输出契约与模板](references/design-md-template.md)，局部更新读取受影响要求；按 [生成条件与覆盖清单](references/frontend-audit-checklist.md) 核对当前模式的依据及适用任务能力，避免把所有项目都按后台或移动端检查。
4. **处理缺口。** 有冲突或缺少关键选择时，先形成可审阅的推荐方案，说明现状证据、不宜固化的实现、拟补齐或修改的规则及影响；已有文档说明保留、合并、修正或重写的范围。已有授权覆盖的选择直接执行；仅澄清影响可用性的未知信息或确认尚未授权的关键决策。非关键缺口记录，不阻塞其余已确定内容。
5. **写入规范。** 使用 [输出契约与模板](references/design-md-template.md) 的适用部分，保留设计基础及共用布局的主题入口，在组件/页面模式内整合依据、状态、视口差异和判据；已有文档保留有效结构、内容与确认状态，更新只覆盖本次范围，不因套模板删掉未受影响的规则。用户只要求方案或草稿时保持该状态，不能将未确认提案写为生效规则。
6. **复核并交付。** 按下文完成可执行性复核，说明文件位置、模式、依据文件、更新策略、事实归纳与新增决策、实际验证及剩余缺口。默认在回复中交付这些信息，不另建过程报告。

## 核心约束

### 决策、实现与证据状态

三种状态分别表达，不能用“已确认”代替“已实现”或“已验证”：

- **决策依据：** 既有有效契约、用户已确认方案、授权范围内的设计选择，或待确认提案。
- **实现状态：** 已实现、部分实现、待实现；允许不同规则具有不同状态。
- **验证状态：** 静态核对、实际实测、未验证，并说明证据范围。

采用项目已有承载方式；没有时在相关规则旁或简短的“依据与状态”说明中标注。相同状态可分组说明，不强制每条规则建表。待确认提案不作为硬约束，已确认但待实现的规则可指导开发，但不能声称现有页面符合。

### 写作边界

- 默认使用中文标题和说明，沿用项目名称和定位；保留项目实际 token、字段与组件命名及被工具消费的格式兼容性，不因套模板重命名或重置版本；不复制其他品牌的身份和叙事。
- 规则写清适用对象、动作与可观察判据，避免只有数值、组件名或“统一风格”等形容词。
- 只写当前范围需要的已有或已确认规划能力；不为填满模板发明大量组件或无关平台要求。
- 标题、顺序和状态表达按项目适配；只有真实机器契约或用户要求才固定结构与字段。
- 未确认、未实现、未验证与不适用分别标注，不用“无代码”否定初始化，也不用建议内容冒充项目事实。

## 产出边界与交付

首次生成或获准补全文档时落实下述产物边界；仅保存、逐字保存或局部更新沿用有效基线，不为补边界扩写或重排，范围外缺口在交付中说明。

交付目标 DESIGN 的新增或修订内容及来源、模式、状态和验证限制；默认只修改规范。仅保存或局部更新保留有效基线，不为补齐模板重做设计决策；未确认提案不转为生效规则。

### 产出文档边界

文档边界遵循 [全局规范](~/ai-agent-config/config/force/document-boundaries.md)。DESIGN 维护界面与交互契约、适用范围和维护要求；架构机制、业务需求及临时复测记录由相应文档维护，token 等已有机器事实源只引用，不另立数值定义。

## 验证与完成标准

### 可执行性复核与后续校准

两种模式均按 [任务与能力规范覆盖](references/frontend-audit-checklist.md#任务与能力规范覆盖) 复核适用的任务状态、组件状态及恢复路径，不只检查默认外观。

- **已有页面：** 选择本次范围内的代表性页面，检查能否按规范找到布局、组件与 token 入口，理解接入方式并判断适用状态。实测证据按 [前端验证规范](~/ai-agent-config/config/force/frontend-verification.md) 处理；不能运行时仅做静态复核。
- **没有页面：** 用需求中一条代表性任务做纸面走读，检查规则能否确定页面结构、必要组件角色及可观察验收判据。无需创建页面或原型；只说明规范可执行性已检查，界面实现与渲染尚未验证。
- **首次落地后：** 在用户要求的后续规范更新中，对照代表性实现与证据补充真实入口、校准已确认规则并更新状态。实现偏离时先判断修实现还是经过授权修改规范，不自动把偏差写成新标准；初版交付不依赖未来页面完成。
