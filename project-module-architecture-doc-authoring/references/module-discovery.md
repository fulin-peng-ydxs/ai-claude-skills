# 技术主题发现与证据规则

本文维护模块及技术专题的边界识别、事实来源、输出路径和核查要求；产物内容由 [输出契约](output-contract.md) 维护。

## 从问题识别主题

先明确文档要解释的技术问题，再定位代码范围。候选依据包括用户目标、API/CLI 边界、数据所有权、平台能力、运行拓扑或技术机制；不把目录直接当作主题。

| 主题 | 典型范围与关注点 |
| --- | --- |
| 功能模块 | 页面/API、业务服务、数据及模块边界；解释实现，不展开每个业务环节的全部规则 |
| 平台/技术子系统 | 鉴权、调度、消息、缓存、文件等共享机制、扩展点与生命周期 |
| 数据或集成 | 数据来源、处理、存储、质量/口径、协议映射、消费者与失败恢复机制 |
| 前端技术 | 路由、状态管理、API 客户端、权限接入、组件复用及构建关系 |
| 系统架构 | 能力、代码包和运行单元映射，主要调用、共享技术机制及边界 |
| 部署架构 | 制品、配置、依赖装配、网络与存储、发布和恢复机制，不绑定某服务器操作清单 |
| 专项技术解析 | 围绕一个具体机制跨目录或跨模块追踪，例如配置覆盖、事务一致性、插件加载 |

按阅读与维护边界拆合：不同问题有独立消费者、契约或变更边界时可拆；多个目录只是同一主题的分层实现时合并。用户只要一个技术解析时不自动补齐全套模块、系统和部署文档。

系统总览维护跨主题关系，局部文档维护具体机制；闭环文档维护流程专属状态、权限和字段规则。已有权威说明先核实并复用，发现过期时更新所属正文及受影响引用，不复制一套修正版。

## 事实发现与核查

从 README、AGENTS、现有技术/闭环/API 文档定位入口，再回查路由、页面、服务、存储、DDL、配置、构建、部署和测试。扫描脚本只发现候选文件，不能据目录名判断职责、依赖或已部署状态。

- 关键结论定位到文件及类/函数/SQL/配置键/测试；命令、接口、表、端口、版本、运行单元和依赖方向均回查。
- 事实来源包括源码、机器配置、当前权威文档和实际执行结果。文档说明意图或约束，实现用于核实行为；不把实现与规范冲突解释为规范失效。
- 推断写依据；无法访问或证据不足写待确认与影响。未获取 DDL 时区分实现视图与物理结构；仓库部署定义与实际环境状态分别标注。
- 只在任务需要且安全、成本合理时执行运行验证，记录前提与结果；分析本身不授权写库或变更部署。敏感配置只写位置、类型和用途，不输出真实值。

## 输出路径

1. 用户指定路径优先；已有同主题文档通常原位维护，用户明确要求独立新成果时按其要求保存。
2. 未指定时使用已有架构目录，优先识别 `agent-works/architecture/`，其次项目明确承载架构文档的其他目录。
3. 没有既有目录时使用 `agent-works/architecture/`。

文件为 `<output-dir>/<module-slug>.md`；这里的 slug 表示模块或技术主题，使用稳定 kebab-case，不用临时版本号、日期或人名。保留已有路径与外部引用，无法判断同名文档归属时先查内容；仍有实质歧义再确认。

## 证据与质量复核

验证状态分别记录：

- **已执行**：本次实际运行，另记通过/失败、环境和结果依据。
- **静态确认**：源码、配置或测试确认入口/机制存在，未验证运行行为。
- **待确认**：当前缺证据、存在未解冲突或依赖不可访问。

风险按影响标高/中/低，并区分已确认问题、推断、已知限制和证据缺口。安全、数据损坏或严重不可用为高影响；结果偏差、性能退化或局部不可用按实际影响判定。没有明确风险时说明检查范围，不能称绝对无风险。

保留有效机制、约束和证据；删除历史流水、旧计划、无依据推测、来源项目残留及无关模块细节。选择一条代表性技术链路复核解释与源码一致，箭头说明调用、数据或依赖语义。索引只负责导航，README 保留最小使用路径，不因去重删掉理解与操作上下文。
