# 模块架构文档编写

## 职责与边界

面向开发者解释一个明确技术主题的当前实现、工作原理、依赖与约束，帮助定位代码、接入扩展和判断变更影响。主题可以是功能模块，也可以是系统架构、部署架构、配置装配、鉴权、缓存、调度等技术解析，不要求对应单一目录或独立运行单元。

本文维护执行流程；[主题发现与证据规则](references/module-discovery.md) 维护边界、路径和事实核查，[输出契约](references/output-contract.md) 维护技术文档内容与深度。

- README 负责最小运行与使用入口；本文产物解释该主题如何工作。
- 业务闭环文档负责具体业务逐环节的角色、状态、权限、字段赋值及消费口径；技术专题维护共享机制和技术约束，不复制完整业务明细。
- 接手报告负责版本或交付包的完整性评估与接管路线；技术专题是持续维护的实现说明，不复制接手清单。
- 部署架构解释代码与部署材料定义的运行单元、装配、网络、存储及生命周期机制；具体服务器的启停、升级、备份恢复操作清单归运维手册。

## 输入与前置条件

确定项目、技术主题、读者要理解的问题、现有文档和操作类型。先检查已存在的同主题或共享机制说明，避免同一事实另建平行正文；已有授权和明确目标不重复询问。

仅保存时核对已有基线、有效修正和路径，保留证据状态，不重扫或补写。局部更新只维护受影响事实、引用与适用规则；首次生成或整体重构执行下列流程。

## 执行流程

1. **定位主题**：读取项目规则、README、现有架构/闭环/API 文档及相关源码、配置、测试和部署材料。完整项目发现时运行 `scripts/detect_architecture_modules.py <repo-root>`；指定技术主题可直接追踪相关入口，不以扫描目录限制主题。
2. **确定范围与维护位置**：读取 [主题发现与证据规则](references/module-discovery.md)，明确负责的问题、代码跨度、共享机制和排除范围，选择输出路径。系统总览与局部专题并存时先确定共享事实的唯一正文位置。
3. **追踪技术机制**：完整读取 [输出契约](references/output-contract.md)，按主题选择适用检查项。沿入口、核心处理、数据或状态结果、失败边界建立证据链；已有业务闭环只引用所需事实，不重复生成整套流程。
4. **核实与编写**：按发现规则核对路径、API、类/函数、表、配置、测试和依赖方向。解释实际机制与约束；依据不足标明缺口，不把推断写成已验证行为。
5. **联动与交付**：维护同主题原文件，检查相邻文档是否存在重复定义；只同步受影响的 README、AGENTS、架构索引或业务文档摘要和引用，不自动创建其他专题。

## 核心约束

默认简体中文，代码、标识及项目既有英文约定保持原样，用户语言要求优先。只解释已存在的实现，不把未落地方案、设计意图或某环境例外写成通用架构；实现与有效规范冲突时记录差异。

说明为何当前机制产生这些行为和约束，设计动机没有证据则不猜测。候选扫描与源码目录索引不能替代技术解释；只列框架名、类名或配置键不算完成。发现风险不自动修代码、部署或执行数据操作。

## 产出边界与交付

采用输出契约的参考结构，一篇围绕一个可独立理解的技术主题；系统架构、部署架构同样适用。路径按主题发现规则选择，稳定标识沿用现有 `<module-slug>.md` 命名方式，可使用 `system-architecture`、`deployment-architecture` 等主题名。不因目录多就批量拆文档。

产物在范围说明中落实具体技术职责和关联正文归属。报告文件绝对路径、主题范围、关键证据、验证结果和剩余缺口；仅保存或局部修订保留范围外原结构及有效内容。

## 验证与完成标准

- 每篇运行 `scripts/validate_architecture_doc_structure.py <document-path> --custom-structure`；只有明确采用内置模块骨架时省略参数，项目其他固定契约单独核对。技术解析标题不必强套“模块架构”。
- 按输出契约复核适用内容，并沿代表性调用、配置生效或部署装配链路走读：能说明入口、机制、结果、边界和失败定位，不以图表或源码清单代替说明。
- 回查关键事实、链接、锚点、依赖方向、表格和 Mermaid；静态确认与实际执行分开报告。未执行的命令、测试和线上行为不得称为验证通过。
- 核对同主题与跨文档内容归属，正文只维护一次，其他位置保留必要摘要与真实链接。没有独立专题时保持本主题自足，不为分工虚构文件。
