# 页面体验审核

## 职责与边界

审查页面体验与视觉交付质量。聚焦“稳定、统一、直观、克制、细节完整”，不把业务规则正确性当作审查目标。

本文维护审核范围、体验定级与授权边界；[体验检查清单](references/audit-checklist.md) 维护具体检查项，报告骨架按下文参考文件读取。项目设计规则由原事实源维护，不在体验报告另立契约。

### 边界

- 项目没有移动端目标时，不要求移动端支持。
- 不判断业务算法、数据口径、领域规则、权限策略或后端正确性；只记录其可观察的体验影响，领域原因转交业务审核。
- 不用新增复杂功能来修复简单体验问题。
- 不基于个人审美要求重做页面；所有问题必须落在一致性、可用性、清晰度、稳定性或不必要复杂度上。

## 输入与前置条件

输入为页面、模块、PR 或 diff 与可访问的预览环境；未重新指定时继承当前范围，独立全局审核按流程发现入口。无实测能力时保留限制，不降格为已通过验收。

## 执行流程

1. 确定审查范围：
   - 用户指定模块、路由、页面文件、PR 或变更范围时，只审查指定范围。
   - 用户未重新指定范围时继承当前任务或 diff；独立审核且没有范围线索时，才覆盖当前项目所有可访问页面，从路由、菜单和页面目录识别入口。
   - 优先覆盖新增页面、近期改动页面、用户可导航页面和核心工作流页面。
2. 读取项目页面规范：
   - 优先读取 `DESIGN.md`、`AGENTS.md`、`README.md`、页面模板、布局规范、组件目录、主题 token、同类页面实现。
   - 若项目没有明确设计规范，以当前项目中质量最高、出现频率最高的同类页面作为一致性基准。
3. 选择验证范围与证据：
   - 读取 [前端验证规范](~/ai-agent-config/config/force/frontend-verification.md)，确定相关视口、输入方式、平台能力和消费者；复用已有有效证据。
   - 布局或交互改造以可获得的改动前页面、原型或已确认任务路径为基线，按清单比较操作成本；基线不可得时说明限制，不凭当前页面可用就宣称体验改善。
4. 完成适用场景的页面实测：
   - 使用项目可用的预览、浏览器与交互工具，按共用方法执行所选场景并记录观察结果；不能以静态检查替代实际呈现或交互证据。
   - 无法实测时，明确对应验收未完成及原因，只对已取得证据的部分下结论，不宣称页面验收通过。
5. 按清单的适用项审查：
   - 读取 [references/audit-checklist.md](references/audit-checklist.md)，具体检查项只在该清单维护。
   - 覆盖风格统一、排版、颜色、字体、交互、状态、动画、说明、控件必要性和冗余交互。
6. 输出可执行报告：
   - 每个问题写清位置、现象、原因、建议和优先级。
   - 不使用“更现代”“更高级”“更有设计感”这类空泛评价。
   - 用户只要求审查时不要改代码；用户要求修复时再实施改动并复测。
   - 修复按既有规范可直接确定时直接实施；需要重新选择布局、层级或视觉方向时配合 `frontend-design`。不因开展体验审核自动启动页面重设计。

## 核心约束

### 核心原则

- 检查用户可观察的一致性：同角色控件、布局及状态是否给出一致线索。代码是否复用由 `frontend-reuse-governance` 判断，不能仅因私有实现或缺少共享 class 判为 UX 缺陷。
- 最小化交互承载。一个用户意图只保留一个主要交互路径；文字、状态、行点击、标签点击、行内操作、键盘操作或附近已有控件能自然承载时，不额外加按钮。
- 优先语义直达。代表可导航、可筛选、可操作含义的状态文字，在安全且可发现时可以直接作为交互目标；除确认、权限、破坏性或异步命令外，不再旁边重复放“查看 / 搜索 / 打开”按钮。
- 拒绝装饰性功能。控件、卡片、统计块、开关、筛选、动画或说明不支持明确用户任务时，应建议移除、合并、折叠或降级。
- 高密工具保持工作导向。后台、仪表盘、数据、管理和研究类页面优先保证可扫描、布局稳定、样式克制、控件可预期，而不是营销式构图。
- 检查状态而不是只看正常态。加载、空数据、错误、禁用、选中、hover/focus、提交中、成功、长内容、极端值、无权限或不可用状态都属于页面交付范围。

### 优先级

- `P0`：页面不可用、关键内容遮挡、主流程无法完成、严重溢出、白屏、交互阻断。
- `P1`：主操作不清楚、关键状态缺失、严重风格不统一、冗余控件造成理解混乱、用户容易误操作。
- `P2`：未阻断使用的排版、间距、颜色、文案或控件细节问题。
- `P3`：可选打磨或长期一致性优化。

本节只定级体验影响。发现明确 DESIGN 违规时关联契约依据，转交 `design-compliance-audit` 判定；联合审核保留合规定级，不能以 UX 影响小降级。同根因按共用方法合并报告，必改问题未解决不判通过。

## 产出边界与交付

首次生成或获准补全文档时落实下述产物边界；仅保存、逐字保存或局部更新沿用有效基线，不为补边界扩写或重排，范围外缺口在交付中说明。

### 产出文档边界

文档边界遵循 [全局规范](~/ai-agent-config/config/force/document-boundaries.md)。正式报告说明本次页面范围内可观察的体验问题、证据与复测结论；业务规则和 DESIGN 契约引用对应事实源，不在体验报告中另行定义。简短审核可并入审查范围。

### 输出格式

按 [文档结构与输出规范](~/ai-agent-config/config/force/document-output.md) 使用**默认骨架**。结论、范围与方式、逐项体验问题及建议、实际检查状态和未验证风险必须保留；结论枚举与优先级语义不变。按页面实际能力选择状态，无问题的分类可合并说明；未实测状态不能当作不适用删除。

生成对应完整产物或获准补全本部分时，读取 [页面体验审核报告](references/output-template.md#页面体验审核报告)；仅保存或局部更新不重新套版。

## 验证与完成标准

核对问题均有可观察现象、位置、影响、建议与证据；按实际测到的页面和状态给结论，未实测不可当作不适用。已授权修复后复测，只有审核请求时不修改代码。
