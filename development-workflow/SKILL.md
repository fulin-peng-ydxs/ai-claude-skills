# 开发计划与实施

## 职责与边界

本文维护计划模式、技术任务、状态汇总和验证安排；需求与验收契约由上游维护，调研、确认和保存沿用需求协作共用契约，产物模板按下文按需读取。

### 职责与入口

计划维护已确认需求的技术方案、任务、依赖、验证安排与进度；业务规则引用上游，任务记录保留必要实际结果和证据入口，完整实施证据由已有实施记录维护，长期事实归架构文档。不因编写计划自动创建留痕或执行开发。

执行前读取 [需求协作共用契约](../requirement-doc-authoring/references/workflow-contract.md)，应用事实、确认、保存和自适应规则。需要保存计划时默认文件名 `plan.md`。

- 用户要求生成、更新或保存开发计划时，按其格式和保存要求交付；明确只要对话方案时不落盘。开发请求中自动调用时，先用会话计划或任务清单组织实施，只有用户要求计划文档或项目规范要求时才保存，不额外创建阶段性文档。
- 简单改动可合并为简短任务，仍保留目标、操作、结果和验证；不为自动调用套满所有章节。纯问答、只审查、仅编写需求/原型或尚未授权实施的讨论，不自动转入开发计划或实施流程。

## 输入与前置条件

### 普通模式与专业模式

未指定模式时默认普通模式；同一计划后续更新继承已选模式，用户要求时切换。不能因为已有 PRD、需求复杂或风险较高就自动切换专业模式。两种模式共用任务粒度、验收、状态与风险要求，仅输入前置和原型准备方式不同；在计划来源处注明模式与依据。

| 模式 | 输入与推进规则 |
| --- | --- |
| 普通模式（默认） | 自然语言、会话结论、功能说明或技术目标均可直接生成计划；有相关文档就继承，不强制先生成闭环文档或 PRD。把明确的目标、范围、行为和验收条件写入计划，无正式编号时用本地编号。涉及页面开发且原型选择尚未明确时，按原型技能询问生成 HTML 交互原型还是结构图原型；不是要求用户事先提供原型。用户可明确不生成，届时记录现有页面/规范/文字方案等依据，不因缺原型文件本身阻塞。 |
| 专业模式（用户指定） | 正式需求文档为前置；涉及页面开发时，还须有覆盖本次页面范围的 HTML 或结构图原型，纯后端/无页面工作不要求原型。已有合格成果直接复用，缺失或过期时列出缺口；已有生成/更新授权则调用对应技能补齐，否则询问用户提供还是协作生成。材料未齐可做调研与计划草案，不宣称最终可执行，不启动依赖缺失材料的页面或功能实施。 |

用户明确描述的目标和范围可作为计划依据，无须为了“已确认”再要求一次形式确认；仍有实质业务或方案歧义时按共用契约处理。普通模式的原型选择未答时不默认选择格式或当作放弃，可继续无关调研和草案，不开始依赖该选择的页面实施。专业模式若用户明确免除文档/原型前置，遵循其要求并标注具体豁免及替代依据，不能声称原前置已满足。

仅请求计划时交付计划；用户要求开发、修复或重构，或明确要求“生成后按计划开发”时，组织计划后沿用该实施授权继续，不要求额外说一遍“开始开发”。自动调用不扩大授权，未解决的关键选择仍只阻塞依赖部分。保存已有成果不因模式检查自动补建文档或原型。

## 执行流程

先区分新分析/生成、局部更新与仅保存已有成果。仅保存时核对原基线及有效修正，保留内容和证据状态，不重跑完整调研或补写；局部更新只执行受影响步骤。适用的范围与写入确认规则继续有效，已有授权不重复索取。

1. **识别操作与输入**：确定模式，定位用户指定的自然语言需求、文档或技术工作目标，区分生成、保存和更新。完整读取本次需求，提取来源、目标、范围、适用的角色/流程/数据/权限/接口、验收和未决项；按模式判断前置，不因缺文件否定明确的需求。同一成果按授权更新，不因已有文件另建平行计划。
2. **核实实现依据**：调研相关代码、页面、服务、配置、数据库/SQL、权限、测试及项目规范，记录关键路径、接口、类/方法、表字段和状态等可核实依据。缺少访问能力时标注限制，不猜现状。
3. **承接页面与原型**：涉及页面、布局、组件或交互时，读取 `DESIGN.md` 及适用的组件库、页面模板、样板和测试契约；没有相关规范时说明最低 UI 约束。按模式处理原型选择，已有引用必须实际读取，相对路径按引用所在文档目录解析；无需求文档时沿用本次功能目录，不虚构文档路径。页面条件规则见下节。
4. **判断阻塞**：按共用契约先核实事实，再处理实质业务或方案选择。阻塞未决可保存计划草案并标记依赖，不能宣称最终可执行或启动受影响任务；不受影响部分继续。非阻塞项写明影响、确认时点和到期依赖。
5. **编排方案与任务**：以可交付业务能力组织任务，在同一任务中串联目标、现状依据、技术方案、开发步骤及验收；跨任务共用的边界、数据流与依赖集中说明一次。逐项建立需求→任务→验收映射。性能、安全、兼容、SQL、发布等按风险展开，不为套表引入新框架、队列、缓存或配置体系。
6. **交付并复核**：按下方最低内容生成或更新计划，依入口规则决定在会话中表达还是写入文件；初始安排与执行证据分开。保存已有成果不重套模板，更新只反映真实变化，并按状态规则同步关联映射；已有实施授权时继续执行。

## 核心约束

### 默认文档模板与最低内容

首次完整生成默认采用“需求与交付总览→实施方案与任务→验收与交付”三部分，开头简述来源、模式、目标、范围、文档职责及关键阻塞。简单任务可合并，复杂任务在所属单元内展开；最低信息要求不等于独立章节要求。仅保存、局部更新仍沿用有效原结构，获准重构才重新组织。

生成对应完整产物或获准补全本部分时，读取 [开发计划主体](references/output-template.md#开发计划主体)；仅保存或局部更新不重新套版。

实施范围由需求总览维护，不另设范围或增强状态表。事实、业务口径、局部风险、SQL及未决项就地支撑所属任务的方案；跨任务共用规则集中维护，消费任务引用并补差异。不得把原有各章整体搬入“共用方案”。性能、安全和兼容性始终判断适用性，低风险可合并说明依据。下表是信息覆盖要求，不是章节清单：

| 主题 | 最低内容 |
| --- | --- |
| 来源、目标与范围 | 输入文件/会话依据、目标、不做范围、项目事实及限制、输出位置；建议项沿用需求阶段状态，不能自动纳入。 |
| 技术方案 | 整体思路、关键单元的职责与选用依据、逻辑模块/运行服务/一次性任务的区分、数据流、接口、权限、兼容和取舍；按场景串联入口、处理、数据/状态、反馈与失败恢复。 |
| 需求映射 | 每项来源、范围类别、需求阶段处理状态（如有）、纳入判断、计划开发内容、任务、覆盖判断、进度及缺口。详见映射规则。 |
| 任务与依赖 | 任务编号、输入/前置依赖、涉及文件/模块、目标、操作、产出、影响、边界/异常、验证与完成标准、状态及实际结果。详见任务规则。 |
| 测试与验证 | 按风险选择最低充分层级、场景、数据/负载、方法或命令、通过条件、依赖任务；执行后补实际结果与证据。 |
| SQL、发布与回滚 | 适用时说明迁移/初始化、产物进入环境的步骤、配置生效、检查、成功判据、回滚前提及方式；无此变更可合并说明。 |
| 风险、假设与未决 | 依据、影响、处理动作和确认时点；阻塞项明确关联任务，最终可执行计划不得掩盖未决阻塞。 |

### 页面、复用与配置方案

- 逐项承接自然语言或文档中的页面功能点，以及已有原型的相关区域，建立“页面功能点/正式或本地编号 → 实现与组件/模块 → 数据/API、状态/事件、校验、权限、联动与异常 → 任务/验证”的映射。可与需求映射合表，但不能只写“按需求实现”。未纳入项按范围规则记录，不把排除项误标为超范围开发。
- 新增或复杂页面写清页面类型、主操作/内容/辅助区、弹层/抽屉、固定与滚动归属、增长区域、窄屏和低高度退化；更新页面说明变更区、保留区及兼容影响。布局依据关联实际原型，或普通模式明确不生成时的现有页面/规范/文字方案，任务承接主要入口、数据区和加载/空/错误/权限等状态。
- 原型选择、两种格式的制作与验证由 [frontend-prototype-design](../frontend-prototype-design/SKILL.md) 维护。普通模式涉及页面开发时须询问格式，不以改动简单为由跳过询问；已明确选择、已有适用原型或用户明确不生成时不重复问。专业模式核对原型前置；结构图也是有效原型，不因不是 HTML 要求重做。
- 原型未覆盖的关键状态和交互须补清，图中无法表达的规则用文字说明；结构图不证明交互已实现。普通模式明确不生成原型时在计划中写清页面区域、操作和状态依据。两种模式中实质歧义均阻塞依赖任务；已有原型与代码、组件或规范冲突时说明影响，不静默取舍或重做已确认成果。
- 运行时组件先判断现有能力能否覆盖，写明共享入口、真实消费页面、状态/事件契约及验证；不足时先扩展既有能力，确需新增才拆组件产出、至少一个真实样板接入、必要清单/规范维护和验证任务，禁止套外壳后重复手写同类行为。
- 涉及布局、组件配置或页面注册时，确认项目实际机制与事实源：自动发现/继承只验证真实消费，不新增逐页登记；显式登记按本次契约补配置 schema、必要登记、存储、读取与生效；没有平台时不为表格新增体系。不适用环节说明原因即可。
- 配置、偏好、模板和预设覆盖定义/渲染、模型与默认值、权限/作用域、校验、保存、读取、实际消费、生效、重置、回退及旧值兼容。跨场景基础能力先核心模型与约束，再真实样板，最后渐进接入，明确迁移与不做范围。
- 页面方案内融合适用设计和组件/布局维护要求，不能用一张登记表代替实现。安排页面验证时读取 [前端验证规范](~/ai-agent-config/config/force/frontend-verification.md)，只计划适用场景、通过条件及任务，不在计划阶段实测尚未实现页面，也不默认跑全量 E2E。

页面方案写入所属任务，说明原型或获准替代依据、变更/保留区域，并按页面功能点关联交互、组件、API、状态、权限、异常及验收。复杂页面可在任务内用局部表格展开；不默认再建立一套全局页面映射表。复用/扩展/新增判断、接入机制、必要登记及实际消费必须可辨识，不能借表格增加配置体系。

### 性能、安全及其他条件方案

性能、安全和兼容性均需作适用性判断；低风险可在总方案内说明依据，有实质目标/风险则独立展开，并引用需求编号或现有约束。不应把“不适用”写成未核实的“无影响”，也不虚构默认指标。

| 条件 | 必须承接的方案信息 |
| --- | --- |
| 性能与容量 | 需求目标、现状基线/瓶颈、数据量/频率/并发/时限与统计口径；按需选择查询/索引、分页/分批/流式、缓存一致性、异步、事务范围、远程去重与超时、资源上限/释放、前端加载/渲染/请求、降级与容量方案，写明取舍、位置、任务和验证。 |
| 安全、权限与数据保护 | 保护对象、信任边界、入口/数据流及风险；按需说明认证、功能/数据权限、输入/输出、文件/富文本/外部地址、敏感信息传输/存储/展示/日志、凭据、会话/令牌、重放/幂等/限流、审计和第三方依赖；每项写明校验位置、失败默认行为、任务、正反向测试及剩余风险。 |
| 后端与第三方 | 服务与接口契约、事务、日志、异常、幂等、一致性、性能影响；第三方的超时、重试、降级、审计和联调。仅展开实际相关项。 |
| 数据库与 SQL | 字段/索引、迁移、初始化、历史兼容；按全局“写SQL时”注明文件路径、用途、执行时机、影响和回滚或不可回滚原因。 |
| 发布部署 | 构建产物、目标环境、配置生效、初始化与升级的区别、前检/发布步骤/健康判据、监控与回退条件；通用流程与环境实例参数分开，未知参数标待确认，不编造可直接执行命令。 |

性能与安全实际改动必须落到任务、相应验证、必要监控/告警、上线检查、发布/回滚影响及剩余风险。缺少会改变方案或验收的基线、指标或安全边界时处理为阻塞，不能只写原则、工具名或“沿用现有机制”。开发环境不能完成的容量验证要写预发或上线后步骤、责任边界和回退条件；未执行验证不能算已通过。

有实质性能或安全方案时在所属任务中展开上述信息，必要时使用局部表格；仅跨任务共同生效的约束进入共用方案。结构设计、SQL路径和迁移兼容归所属任务，跨模块执行顺序、前检和回退集中在交付安排中引用，不重复维护两份脚本契约。

### 专项工作的方案与验证

按共用契约识别工作类型，将适用信息补入技术方案、具体任务、验证及必要发布/回滚条目；复用上游契约，不复制一份专项需求表。下表是条件最低内容，不要求每次展开全部类型，也不自动执行所列操作。

| 工作类型 | 方案、任务及验证必须承接的内容 |
| --- | --- |
| 缺陷修复 | 复现条件、预期/实际与证据；区分已证实根因和待验证假设，安排定位任务及影响链路检查。回归应能检出原缺陷并验证修复及相邻边界；无法重现旧故障时说明替代证据、验证限制和剩余风险，证据不足时不得声称根因或修复已证实。 |
| 重构或升级 | 保持项与允许变化、共享入口及受影响调用方、依赖/接口/配置兼容；需要时安排新旧切换、调用方迁移和旧实现清理。以契约回归或新旧对照验证行为，说明允许差异；仅编译通过不能证明行为等价。 |
| 数据迁移、补数或修复 | 精确选择条件、源/目标及转换口径、写入顺序与并发影响；按风险安排试跑、备份/恢复，明确重跑幂等或禁止重跑的前提、长批次的断点续跑或安全重跑方式及部分失败处置。验证前后数量、关键值与业务不变量，解释预期差异并处理残差；不能只核对行数或 SQL 退出码，无法回滚时给出前向修复与停止边界。 |
| 异步或第三方链路 | 调用契约、业务完成判据及实际涉及的回调、状态迁移、持久化/查询；按机制确定超时、重试上限与停止条件、去重/幂等、乱序处理、部分成功后的补偿或人工接管。安排对应失败场景验证及必要监控；不适用机制说明依据，不凭空新增队列或补偿系统。 |
| 从零建设或技术验证 | 涉及可运行产物时明确依赖与版本/环境约束、初始化顺序、启动入口和首条可运行链路；未知选择安排有边界的验证任务。验证任务写明假设、实验输入/方法、成功/失败/停止判据及证据，结果回填结论与生产落地缺口；假设被否定也可完成验证任务，不能据此将生产实现标完成。 |

专项信息可追加到现有模板字段或就地引用；每项适用要求须关联任务与具体通过条件，实际证据仍按“任务与验证记录”填写。用户只要计划时保留待实施/待验证，不为补齐证据擅自修复、迁移或部署。

### 需求映射与状态规则

#### 编号与映射

- 沿用上游需求编号，不能重排或改义；无编号的输入可在计划内分配 `L1` 等本地编号并标明来源，避免伪装成正式 PRD 编号。后续正式编号出现时建立对应关系，不静默替换导致历史追溯丢失。
- 必须项、有编号的建议项和明确排除项均记录纳入判断；每个本次纳入项至少有一个任务，每个任务可追溯到需求、验收、现有约束或必要技术依赖。一个任务可关联多个强相关需求，映射逐项列出。
- 范围与需求阶段建议状态引用上游，不另设可选增强状态表；任务状态在任务条目维护，映射中的进度是汇总，更新任务时同步更新受影响的汇总。表格可调整，三个维度不能混为一列：

| 维度 | 值与含义 |
| --- | --- |
| 纳入判断 | `本次纳入`：已确认在本次做；`本次排除`：已确认不在本次做，注明依据/后续条件；`待确认`：范围尚未决定。不能擅自将必须项排除。 |
| 覆盖判断 | `一致`：计划完整承接；`部分覆盖`：有缺口及补齐任务；`未覆盖`：缺任务；`超范围`：计划内容无需求/约束/必要依赖依据；`待确认`：覆盖依据不明；`不适用`：已批准本次排除，不算漏做。覆盖判断描述计划承接，不证明实现完成。 |
| 执行进度 | 沿用任务枚举 `待开始`、`进行中`、`已完成`、`阻塞`、`跳过`，按下方汇总规则得到，不手工猜测。 |

需求总览只承担范围、导航和状态汇总：逐项列出来源/编号、目标与本次交付、任务、验收项及当前缺口。共同的范围类别、建议状态、纳入及覆盖判断可放表前说明，例外逐项标明；这三个维度仍须语义独立，不能以一个“完成”覆盖。每项需求独立成行，即使共用任务也不合并编号。长篇技术说明归任务，操作步骤和预期归验收，表内使用可定位链接。

`部分覆盖`、`未覆盖`、`超范围`、`待确认` 必须关联补齐任务、范围决策、风险或阻塞；无法追溯的开发内容须解释必要性或移出计划。经批准排除的建议项用 `本次排除 / 不适用 / 跳过`，不能作为缺陷计入本次完成条件。

#### 任务状态与需求汇总

- **任务状态**：初始 `待开始`；开始实施或实现已结束但必要验证待做为 `进行中`；受未解决依赖阻止推进为 `阻塞`；产出及必要验证均满足完成标准才为 `已完成`；经范围决定取消或不执行为 `跳过`，注明依据。不得以跳过必要验证完成任务。
- **本次纳入需求汇总**：有阻断完成的未决依赖或必需任务阻塞则 `阻塞`；否则全部必需任务完成且需求验收证据满足才为 `已完成`；已启动或仍待集成验收为 `进行中`；均未启动为 `待开始`。没有必要任务或必需任务被跳过时记覆盖缺口并阻塞完成，不能按空集合或全跳过算完成。
- **范围未决**：汇总为 `阻塞` 并说明待决定的范围，不执行依赖它的任务。**本次排除**：汇总为 `跳过`，保留此前已发生的真实任务记录，不能倒改成“未做”。
- 单个任务完成不代表关联需求完成；可选且不属于完成条件的任务不阻断需求，需明确其依据。多需求共享任务时，需求各自检查验收，不用一个完成状态覆盖全部。
- 变更范围后重新核对编号、纳入判断、覆盖、任务依赖及汇总；只更新有证据的条目，不批量标完成。已有文档状态按这些语义核实，保存原文时不擅自改状态。

### 任务与验证记录

任务按依赖顺序排列，以可独立判断结果的业务能力为粒度；同一能力的前后端、数据与页面操作在任务内按步骤展开，必要时拆可追踪子任务。多个能力共同依赖且有独立产出的基础工作可设共享任务；不把无依赖关系的大块工作塞进同一任务。接口契约确定前不安排依赖它的联调，实现之后安排对应回归；前置测试设计可先进行。

#### 单个任务模板

每项任务按“目标与现状依据→实施方案→开发步骤与产出→完成条件与当前结果”展开，头部标明来源、依赖、状态及验收引用。现状注明可核实来源，方案说明复用入口、选择依据和入口到结果的链路，风险及未决项说明影响、处理动作与解决时点。简短任务可改为等价表格，但不能省掉操作、产出、完成标准或实际结果；任务总览表不能替代详细任务。

生成对应完整产物或获准补全本部分时，读取 [单个开发任务](references/output-template.md#单个开发任务)；仅保存或局部更新不重新套版。

阅读组织与去重按共用契约引用的全局文档规范执行；本技能以可交付任务为单元，完成条件引用具体验收。影响范围须包括修改入口、受影响消费方、保持不变的行为和必要回归，不能用修改文件清单代替。

操作和产出必须具体，不能仅写“实现功能、联调上线”。验证可引用集中记录，但须能定位具体场景及通过条件。进行中或完成的任务记录已落地文件/模块、接口或页面行为、数据结构、权限、异常处理、验证证据，以及与计划的差异、降级、额外影响和未完成缺口；不只重复状态。生成计划前已经完成的工作按真实证据填写，不套用初始状态。

#### 验证计划与实际记录模板

验证按风险选择领域/单元、接口、页面交互、权限/数据范围、组件配置真实消费、性能容量、安全正反向、兼容回归和异常边界；不机械为每类建立空栏目。自动检查按实际入口组织；人工验收按真实业务操作顺序组织，跨任务流程只写一次，各步骤关联需求和任务。每个可独立判定的检查点有稳定编号、前置、操作、预期、实际结果及证据，多个入口或边界允许分别记录结果；不能用一条长流程的单一“通过”掩盖部分失败。需求/任务关联一致的检查点在组头声明共同关联，关联不同的在对应检查点注明差异；跨任务流程不能只列整组任务而让读者推断失败归属。共用账号、版本、数据与环境写一次，场景补差异，不能只留下“补测试”的汇总任务。

生成对应完整产物或获准补全本部分时，读取 [验证项与执行结果](references/output-template.md#验证项与执行结果)；仅保存或局部更新不重新套版。

验收项维护验证结果，任务维护实施结果并引用验收，需求表仅同步汇总；保留证据日期及适用版本，不跨版本无依据沿用。更新时将有效修正融入当前结论，不按日期持续追加平行方案；已有详细记录只引用，未有承载处时保留必要证据，不为重构新建过程文档。

计划阶段只写验证安排，实际部分保留 `待验证`，不虚构命令已执行。执行或更新时填写真实命令、用例范围和结果；非命令验证记录可复现操作步骤。失败与未执行项必须关联影响和后续动作，不以“已完成”代替证据。

涉及性能或容量改动时，另在相应验证项记录下表：比较须使用可比环境、数据规模、负载和统计口径；条件不同应说明，不能直接声称性能改善。基线缺失须记录补测安排及其影响，实际验证后填写资源占用和未达标处置，不只记录是否通过。

```markdown
| 需求/指标 | 环境、数据/负载及统计口径 | 基线结果 | 变更后结果 | 资源占用（适用的 CPU/内存/IO/连接等） | 目标阈值与判断 | 未达标处置或未执行原因 | 证据/后续安排 |
| --- | --- | --- | --- | --- | --- | --- | --- |
```

页面验证承接原型或已明确页面方案的主要区域、操作与状态及响应式/低高度要求；配置验证覆盖展示、保存、读取、生效、重置、非法值与旧值；组件验证证明真实消费和正确接入机制；基础能力必须有真实样板。需求与页面功能点的验证可直接引用其验收，不再维护平行清单。

### SQL、发布与回滚模板

仅在实际涉及时展开，具体要求见条件方案；无相关变更可简述依据。初始化与升级步骤分开，未知环境参数和命令标待确认，不能拿占位内容作为可执行指令。

生成对应完整产物或获准补全本部分时，读取 [SQL 与发布回滚](references/output-template.md#sql-与发布回滚)；仅保存或局部更新不重新套版。

## 产出边界与交付

交付会话计划、任务清单或授权的 plan.md，保存条件沿用职责与入口规则。首次生成或获准补全时在成果中说明计划职责和上游边界；仅保存或局部更新不为补边界扩写或重排，缺口在交付中报告。

## 验证与完成标准

### 交付检查

- 模式与前置状态准确：普通模式没有强制补 PRD，页面原型选择已有答复或明确标为待选择；专业模式的需求文档及适用原型真实、覆盖当前范围。缺口或豁免明确，不能把草案交付说成前置已满足。
- 检查需求→任务→验收双向可定位，无孤立需求、任务或必要验收；从审批者角度只读一个任务就能判断依据、选择、影响和可执行性，从验收者角度沿流程能逐项操作、判定并定位失败责任。
- 从接手开发者角度走读一条需求到接口、处理、数据/状态、反馈与失败恢复，检查输入、依赖、任务操作和验收是否衔接；新设计标待实施，不能只列技术栈或文件名。
- 本次纳入项无未解释缺口，每项任务有来源和产出；范围、覆盖与进度含义分开，必要验证缺失不算完成，排除建议不算漏做。
- 页面方案承接真实原型或获准替代依据，复用与配置有实际消费，适用的性能/安全/迁移/发布要求落到任务和验证，未额外引入无必要体系。
- 按全局阅读路径规则检查任务与验收：跨任务流程的每个检查点能明确关联需求和任务，影响范围覆盖消费方与回归，发布安排包含产物接收方及交付方式；未知项明确其阻塞范围，不编造。
- 文档与关联引用一致，实际结果有证据，未验证和阻塞如实披露；表格齐全不能证明计划可执行，不额外新建阶段性报告。
