# 需求协作共用契约

供需求闭环、正式需求、页面原型和开发计划技能执行时读取；只维护这四类工作的事实调研、成果继承、确认、保存和表达规则，各阶段的内容、编号与产物由对应技能维护。目录与通用文档要求沿用 [协作规则](~/ai-agent-config/config/force/collaboration-rule.md) 和 [文档边界](~/ai-agent-config/config/force/document-boundaries.md)，不复制其全文。

## 事实与继承

- 先识别目标项目、用户要求的操作和成果。输入按内容语义、用户指向及可证明的文档关系选择，不绑定固定文件名，不把同目录材料自动当作当前需求的上游。
- 按本次链路调研相关代码、页面、接口、服务、配置、权限、测试及可用数据库结构和数据；性能、安全等只调研会改变需求或方案的事实。记录必要的文件路径、接口、字段、状态及来源；无法访问的依据标明限制，不能编造或把可自行核实的事实转交用户拍板。
- 区分项目事实、已确认结论、推断和未决问题。代码只能证明当前实现，不能自动证明业务必须如此。结合项目领域解释关键术语、角色、对象、状态和口径；只有领域差异实质影响规则且无法查明时才询问。
- 继承上游的功能点、入口、流程、状态、数据、权限、异常、范围、建议项状态和确认结论，不重新发散一套平行需求。新事实与结论冲突时说明依据、影响和待决选择，不能静默改写。
- 优先沿用有效的项目规则与同类模式；新抽象须有现有能力不足的依据。跨文档只保留本职责所需摘要与追溯，业务要求、实现选择和实际验证证据不能混为一谈。

## 确认与推进

| 类型 | 判断及动作 |
| --- | --- |
| 阻塞选择 | 缺失结论会使当前阶段无法成立，或实质改变目标、范围、流程、状态、权限、数据或接口契约、方案取舍、上线或验收；说明影响、推荐方案和理由，等待相关选择后再做依赖工作，其余工作继续。 |
| 非阻塞未决 | 不影响当前阶段启动，但后续仍需业务决定；记录影响、确认时点和依赖，用户愿意当次决定则处理，未答不等于同意。到达依赖点仍未解决时转为阻塞。 |
| 可自行决定 | 有项目依据、低风险且可回退的常规细节；直接处理，必要时说明依据，不逐项征求批准。 |

- 先核实事实再分类；不能仅因为涉及数据结构或技术细节就要求用户选实现。问题多时按影响分批，分类清单和提问保持易答，不设置机械总数。
- 既有确认与授权持续有效；只确认新增的关键差异，不重复要求批准相同范围、目录或布局。
- 写入授权与内容确认独立：用户要求保存即可保存当前草案，未决和假设保持原状态；保存不代表批准。阻塞项未解决时不得标成最终确认成果，也不据此执行依赖该结论的实现。
- 当前阶段完成不自动授权下一阶段、生产开发或其他产物；是否切换由用户请求和对应技能触发规则决定。

## 保存与已有成果

- 首次生成先选适用结构；保存已有成果以用户指向内容及后续有效修正为基线。仅有摘要就保存摘要，不擅自扩写为全文；多个候选无法判断时才确认对象。
- 保存或局部更新沿用原章节、层级和内容范围，保留有效细节、理由、例子、表格、图示、引用及各项确认状态。可修正格式、指代和措辞，去掉寒暄与执行预告；不得摘要化、自动转为其他文档或添加额外产物。明确要求逐字保存时保留原文。
- 后续补充融入对应位置，形成连贯正文；不靠附加聊天全文、旧稿或重复附录代替整合。仅在用户要求重构、精简、拆分或转换时执行相应结构变换；实质冲突保留待确认状态，不静默取舍。
- 路径按全局目录规则确定，并检查目标文件：同一成果在既有更新授权内原位维护；独立新需求选对应目录，不覆盖旧成果；同一成果但写入意图不明时才确认，不能因文件已存在就另建平行版本。默认文件名由阶段技能规定，用户指定优先。
- 写入前后对照基线检查内容、确认状态、范围、引用和新增差异；标题齐全或字数增加不能证明完整。交付说明路径、新建或更新、未决项及适用的验证结果，不额外创建过程报告。

## 范围与自适应表达

- 先识别常规功能新增/变更及适用的专项：缺陷修复、重构/升级、数据迁移/补数/修复、异步/第三方、从零建设或技术验证；同一工作可组合多类，性能与安全仍按风险判断。类型用于选择当前阶段的最低内容，不改变技能触发条件，不强制补齐“闭环→PRD→原型→计划”全链路，也不自动创建专项文档。
- 首次生成或获准补全时，将专项要求并入对应需求、方案、任务和验收条目，沿用项目已有契约与证据；交付前检查每个适用要求是否有具体承载、依据和后续验证。不能仅写“已考虑迁移/兼容/异常”；不适用与未知按下方规则处理。仅保存或局部更新时不追补授权范围外的专项内容，必要缺口在交付中说明。领域专属口径从项目或专项依据取得，不凭通用模板补造。
- 从零建设以目标、外部约束和已确认选择为基线；尚未建设的代码、数据或规范标为待建设，区别于无法访问，不要求提供不存在的历史实现。技术验证允许结论尚未确定，但验证目标、边界和判断方法必须明确，验证成功不等于生产可用。
- “必须实现 / 建议实现 / 暂不实现”互斥，同一项只登记一次。建议项处理状态统一为 `本次纳入`、`后续建议`、`已实现`、`待确认`、`不纳入`；`已实现` 要有真实证据。建议项获准纳入可以保留其建议来源，但属于本次验收范围，不再另列一份必须实现。
- 结构策略、条件裁剪与阅读组织统一读取 [文档结构与输出规范](~/ai-agent-config/config/force/document-output.md)，应用其中“模板与结构选择”和“面向读者的组织与审阅”。本流程的闭环、需求和计划采用默认骨架及条目模板，跨模块、权限、迁移、批处理或高风险变化展开所属技能的条件模块；原型按所选形式承载。
- 自适应改变章节组织，不降低信息粒度：每个功能点、正式需求项、页面功能点、开发任务和验证项在所属阶段均须逐项可辨识、可追溯，不能将多个条目压成一段概述。合并后仍保留各自的操作、结果、边界和适用字段；共用规则可集中定义，但条目须明确引用并补充差异，不能用“同上”“按需求实现”掩盖缺项。
- 各阶段语义要求由所属技能正文维护，模板承载结构、字段与必要填法；首次完整生成须形成可交接正文，不能以主题检查表替代本阶段成果。
- 各阶段按所属技能确定业务规则、验收条件和状态的维护位置；闭环结论、正式需求契约、计划实施结果与实际验证证据不能混写为同一状态。
- 性能、安全和兼容性必须判断，但低风险内容可合并说明，有实质目标或风险时展开；不虚构指标或引入无必要的技术设施。
- 用一条范围内的代表性场景连接前提、操作、系统反馈、数据/状态结果、交接和失败恢复，检查读者是否知道下一步与成功判据；示例只解释既定规则，不新增需求或作为实现、验证证据。已有成果覆盖该链路时直接核对，不为走读再写一遍或擅自扩写保存基线。
