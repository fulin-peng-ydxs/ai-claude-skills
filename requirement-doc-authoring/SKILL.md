# 需求文档编写

## 职责与边界

本技能编制可追溯、可验收的正式需求，不承担内部实现拆分或实施验证记录。

本文维护需求生成流程、编号、最低内容和验收规则；[产物模板](references/requirement-template.md) 维护输出骨架与字段，调研、确认和保存规则由下述共用契约维护。

仅讨论粗需求或功能闭环时，由 [requirement-closure-design](../requirement-closure-design/SKILL.md) 承接；本技能只在明确请求正式需求成果时进入。

## 输入与前置条件

输入为明确的正式需求请求、已有需求或闭环成果及项目依据。定位目标项目、操作类型、当前基线和有效确认；已有闭环可直接继承，无闭环文档时按实际请求和可验证事实形成需求，不强制补建上游文件。

执行前读取 [需求协作共用契约](references/workflow-contract.md)，统一事实调研、上游继承、确认、保存和自适应规则；不要重新执行已经完成的闭环分析。只提供闭环材料而未请求正式文档时，不自动转换或落盘。

## 执行流程

仅保存已有成果时，核对用户指定基线及有效修正、路径和确认状态后直接落盘，不执行下列生成流程中的重新调研、编号分配或原型补做；缺口在交付中报告。局部更新只对受影响范围执行适用步骤；首次生成、获准补全或重构按授权范围执行。

1. **确定操作与基线**：区分首次生成、保存已有成果、局部更新和重构；定位目标项目、当前需求及对应目录。保存原文或局部修改不触发整份模板重写，也不因保存而追加原型。
2. **核实并继承**：按共用契约读取相关项目依据及上游结论。逐项核对功能点、页面承载、状态、权限、范围和确认状态，记录冲突和缺口；事实能查证的先查证，只有实质选择才提问。
3. **确定内容规模**：按下方最低内容与条件模块选择结构。区分业务必须满足的外部行为与开发实现选择；表字段、接口字段、事务或配置细节仅在属于已知事实、业务约束或影响验收时纳入。
4. **处理页面协作**：涉及页面时读取项目设计规范、组件库、页面模板、同类页面和验证契约。说明页面清单、原型需求及理由、输出位置、关键布局假设与未决项；已有授权直接沿用，只有新增关键选择才等待确认。
5. **形成成果**：按用户授权写入草案或确认成果，分配或继承稳定编号，完成需求与验收追溯。必要原型由独立技能制作或复用，并回填真实路径。阻塞项或必要原型尚未解决时可保存草案，标清影响和依赖，不伪装成最终可实施版本。
6. **复核交付**：按本文验证与完成标准验证语义、范围、状态和引用，报告文件、成熟度及未决项，不自动生成开发计划或生产代码。

## 核心约束

### 编号与范围

- 每个可独立验收的需求项使用稳定编号 `R1`、`R2` 等；必须、建议及暂不实现项均编号，沿用已有编号与含义。一个编号不混装无依赖关系的能力，不因调序、合并表述而整体重排，不复用废弃编号。
- 新增或实质变化需新增编号，或明确记录原编号的范围调整及原项如何处理；相关页面和验收同步更新，不能使下游误认为含义未变。
- 范围类别、建议项状态及互斥规则按共用契约执行。每项有来源/依据；必须项与 `本次纳入` 的建议项属于本次验收范围，未纳入项不混入通过条件。
- 同一需求在功能、数据接口、页面和验收中使用同一编号。范围及建议状态集中维护，其他章节引用；优化建议如为同一项则补价值或纳入条件，不再登记第二份。
- 更新建议状态须基于最新确认或真实落地证据；未实现的不能写 `已实现`，已有实现也不能代替本次变更验收。
- 主动检查可提升业务价值或使用体验的增强机会，但不为凑章节制造建议。新增增强不得改变核心闭环或扩大必须范围；会明显增加开发量、改变流程或引入新依赖的，未经用户明确纳入前默认标为 `后续建议`。已确认纳入的结论继续有效，同一建议的状态只在范围表维护。

### 文档结构与最低内容

按共用契约读取全局阅读组织规则，以R项为需求契约单元。首次完整生成采用“范围与需求总览→需求详情→跨需求流程与验收→待决事项与推进条件”的默认骨架，开头说明背景目标、文档职责及确认状态。简单局部变更可合并，复杂需求在所属R项或共用单元内展开。每个需求项、页面功能点及验收条件须独立可辨识，不以汇总表代替详细正文。保存已有成果保持原结构。

对应结构见 [正式需求产物模板 · 文档默认骨架](references/requirement-template.md#文档默认骨架)。

现状依据、角色、数据接口、页面承载、边界异常、性能安全及兼容要求归所属R项；确实跨R项共同生效的内容才设共用单元。性能、安全及兼容性不能省略适用性判断。各主题最低内容如下；模板负责结构，本表及条件模块负责语义要求：

| 主题 | 最低信息 |
| --- | --- |
| 背景、目标与项目现状 | 为什么做、预期效果、当前实现与问题、关键事实来源及限制；事实和目标分开。 |
| 角色、场景与范围 | 使用者、权限和数据范围、典型场景；每项编号、内容、来源、范围类别，建议项的状态、价值及纳入条件；暂不实现项说明原因与后续触发条件。 |
| 详细功能需求 | 每项的前置条件、操作流程、输入输出、校验、系统反馈、状态、边界条件、异常与恢复、权限和数据范围、对已有功能的影响。按相关性覆盖增删改查、筛选、导入导出和数据一致性，不为凑模板扩功能。 |
| 数据与接口契约 | 影响上下游、业务边界、兼容或验收的数据、字段、接口、流转和一致性要求；既有事实给依据，新契约标清确认状态。内部类、函数和调用编排留给计划。 |
| 页面与交互 | 按“页面需求”组织，引用需求编号；不涉及页面时简述原因。 |
| 性能、安全与兼容性 | 必须判断适用性；存在实质目标或风险时按下方模块展开，不涉及或低风险时可合并说明依据，不虚构“无影响”。 |
| 验收标准 | 每个本次纳入项至少一条可观察、可执行的验收条件和验证方式，引用需求编号；异常、权限、数据与非功能边界应能验证。 |
| 建议开发顺序 | 简单需求说明单阶段及理由；复杂需求写阶段目标、覆盖编号、前置依赖、模块/页面关系、可验证里程碑及需另行细化的模块。不写工时或人员排期。 |
| 风险、假设与未决项 | 分类、依据、影响和确认时点；草案可含阻塞项，最终确认成果不得掩盖阻塞项。无未决项无需空章节。 |

业务规则与单项验收条件在所属R项维护；复杂页面的共用布局、状态、返回机制在页面单元维护，R项引用并补业务差异。跨需求流程及集成验收集中维护，通过检查点关联各R项；验收索引只链接已有条件，不再复制单项标准。仅单项需求时可将跨需求部分省略或并入R项。

#### 范围与单项需求模板

范围默认集中登记，建议和排除项的条件按编号规则填写；普通功能逐项展开详细需求，简单项也应能完整辨识参考模板中的适用字段。

对应结构见 [正式需求产物模板 · 范围与单项需求](references/requirement-template.md#范围与单项需求)。

#### 验收与推进模板

对应结构见 [正式需求产物模板 · 验收与推进](references/requirement-template.md#验收与推进)。

每个本次纳入R项就地列出可观察的验收条件，覆盖适用异常、权限和非功能目标；跨需求条件说明每个检查点对应的R项，共同关联可在组头声明，差异就地注明。验收条目使用可定位且更新时稳定的标识，沿用已有标识，不因移动重编号；验证方式是计划，不填写实际通过结果。简单需求的推进顺序可用“单阶段及理由”替代表格。优化建议在对应R项补充价值、成本或依赖，范围表维护其状态。

### 专项需求的条件内容

以下要求只在已请求的正式需求成果中按类型适用，融入背景、对应 R 项及验收，不新增整套平行模板。内部处理方案留给开发计划；纯技术项可用运行触发与可观察结果表达，不虚构用户页面。

| 工作类型 | 需求与验收必须明确的内容 |
| --- | --- |
| 缺陷修复 | 预期/实际差异、触发条件与已知复现证据、影响范围、修复后的行为及需保持的相邻行为；不可复现时保留证据缺口，不能将猜测原因写成需求事实。 |
| 重构或升级 | 对外行为、数据与接口等必须保持的契约，获准变化及兼容边界；验收覆盖保持项与变化项，不把技术替换视作新增业务功能。 |
| 数据迁移、补数或修复 | 对象/时间/归属等选择边界、来源与目标口径、冲突/重复/缺失数据处理、历史兼容及业务可用性；明确结果核对口径、允许差异及未解决差异的处置，不只验收执行成功。 |
| 异步或第三方链路 | 受理与完成的区别、业务状态和终态判据、结果查询/通知与交接；按机制说明重复、乱序、超时、部分成功时的外部行为、恢复入口及责任边界，不承诺外部系统未支持的能力。 |
| 从零建设或技术验证 | 首期最小可用范围、外部依赖与约束；验证类明确待证假设、输入条件、成功/失败/停止判据和结论适用范围，不把待验证选择写成既定生产要求。 |

### 页面需求

#### 页面与通用能力判断

- 覆盖本次新增或更新的页面、弹窗、抽屉、表单、表格、图表、设置和配置入口。先判断普通页面、复杂工作台、可配置页面或基础能力建设，不假设项目已有设计系统、布局平台或配置中心。
- 将适用的 `DESIGN.md`、组件库、页面模板和视觉验收方式作为依据；缺失时说明本次最低交互约束，不编造组件能力。
- 需求阶段只识别已有通用能力、可能新增的复用诉求、受益页面/场景与配置承载；具体组件名、拆分、注册和实现由计划决定。已有明确项目契约仍须遵守。
- 配置、自定义、偏好、模板或预设必须说明：谁定义/配置、展示或渲染、保存及位置、读取、实际消费、校验，作用域、默认值、非法值、何时生效/失效、重置和回退。只保存没有消费路径不构成闭环。
- 跨页面或模块复用的基础能力要有真实样板场景、渐进接入范围与不做范围，不能按单页临时功能定义，也不借机扩大本次实施。

#### 每个页面的承载信息

可使用 `P1` 等页面标识，至少保留以下适用信息：

- 名称、类型（新增/更新/弹窗等）、对应需求编号、入口与页面职责，数据来源、权限与可见性。
- 结构与范围：页头/工具栏/主区/侧栏/底部等区域、主次关系、主要展示或编辑字段、操作区、固定与滚动归属、长内容处理；更新页面写清变更及保留区域。
- 弹层和返回路径：触发、承载内容、提交/取消/关闭、刷新与回流；无相关行为时不填空模板。
- 关键状态：按业务覆盖加载、空、错误、权限不足、保存中/失败、禁用及窄屏或低高度退化。
- 布局依据与通用能力：引用实际原型，或说明不生成原型的理由及替代依据；列已有能力、可能新增诉求和配置化承载，不提前指定内部实现。

逐项覆盖本次页面功能点，引用需求编号，并说明默认展示、用户操作、输入/校验、状态变化、提交/取消、刷新与跨功能联动、适用的加载/空/错误/权限反馈及验收引用。共用状态可在页面层集中定义，功能点补差异，不机械为每个控件重复全套状态。

单R项独占的页面信息直接并入该R项；跨R项的复杂页面按参考文件中的页面单元集中维护，功能点引用R项及其验收，仅补页面特有差异，不重新抄写业务操作、校验和状态规则。字段要求以前述说明为准。共用状态可引用页面层定义；适用状态必须有明确行为，不能用一个“状态齐全”结论代替。

对应结构见 [正式需求产物模板 · 页面与页面功能点](references/requirement-template.md#页面与页面功能点)。

#### 原型协作

- 新增页面须有符合需求的 HTML 或结构图原型；更新页面按 [frontend-prototype-design](../frontend-prototype-design/SKILL.md) 的“页面范围与输出”判断，来自专业模式计划的补齐请求还须覆盖其本次页面范围。执行需要的制作或更新时读取该技能，格式未明确时由该技能询问选择；用户明确指定的格式、范围或不制作原型要求优先，记录替代布局依据与剩余歧义。
- 两种格式的制作、命名、交互/状态表达和各自验证由原型技能统一维护。已有合格原型直接复用，继承已有确认；原型与需求冲突时显式处理，不以原型改变业务范围。
- 页面条目引用实际产物路径，相对路径以需求文档目录为基准；已有 HTML 或结构图时不重复另画一套布局图。结构图的操作和状态说明须纳入需求追溯，不能因没有可点击页面而丢掉交互要求。
- 原型尚缺、验证失败或受环境限制时，文档中说明状态、影响及后续动作，不写不存在的文件引用，也不声称页面已验收。用户仅要求保存现有成果时保留缺口，不自动补做。

### 性能、安全与兼容性模块

以下是需求目标，不提前指定缓存产品、中间件、加密算法等实现。每个实际要求关联需求编号，并在验收处有相应验证。

| 维度 | 按相关性展开的信息 |
| --- | --- |
| 性能与容量 | 适用操作、数据规模与增长、频率/并发、响应时间/吞吐/批处理时限/页面体验；目标的负载条件、统计口径、基线或依据、阈值、超限时表现与降级边界。只保留会改变方案或验收的指标，不凭空设数值。 |
| 安全、权限与数据保护 | 保护对象、入口与风险场景、身份/功能权限/数据范围、输入与文件校验、敏感数据传输/存储/展示/日志、凭据、审计、重放或滥用等适用目标；明确允许和禁止行为、失败边界、验收结果及项目规范/法规/外部契约依据。 |
| 兼容性 | 历史数据、旧接口、客户端/浏览器、配置、部署与上下游契约的适用兼容边界及影响。 |

存在新增入口/接口、权限或数据范围变化、敏感数据、文件/富文本、外部回调、第三方集成或高风险操作时，安全要求不能仅写“沿用现有机制”。缺少基线、负载、指标或合规依据时记录缺口，按影响分类；未查明不能按不适用处理。可在所属R项用“场景—目标/边界—条件/依据—验收”表达；跨R项共用目标才集中成表并明确适用编号。

有实质目标时默认按参考文件中的条目表展开，复杂规则补充正文；没有实质目标时依前述规则说明判断依据。不同目标可分行引用同一需求编号，验收标准与此处相互引用，不重复定义阈值或权限口径。

对应结构见 [正式需求产物模板 · 性能与安全条目](references/requirement-template.md#性能与安全条目)。

## 产出边界与交付

交付正式需求正文，包含本次范围、稳定编号、业务与适用的页面/数据/外部契约、确认状态和可执行验收条件。目录按共用契约确定，默认保存为 `requirement.md`，用户指定优先；保存草案不代表内容已获确认。

首次生成或获准补全需求文档时，在产物自身说明：本成果维护业务目标、功能与页面需求、数据和外部契约、确认状态、性能安全边界和验收标准；内部实现拆分归开发计划，实际落地及验证证据归开发计划或已有实施记录。复用已有用途或范围说明，不另加同义章节。仅保存、逐字保存或局部更新时保留授权基线，不为补边界扩写或重排；缺失说明在交付中报告。

首次完整生成或获准补全时读取 [正式需求产物模板](references/requirement-template.md) 的适用单元。仅保存或局部修改时保留有效原结构，不补做授权范围外的产物。

原型按“页面需求”中的触发规则由原型技能制作或复用，需求文档维护真实路径和状态；不自动生成开发计划、生产代码或实施验证记录。建议开发顺序仅表达依赖与里程碑，不替代实现拆分和排期。

## 验证与完成标准

以下完整性检查用于首次生成或获准补全；局部更新检查受影响部分，仅保存时对照基线检查内容、引用、范围和确认状态，不以检查为由补写范围外内容。

- 上游适用内容均有承载，需求编号稳定，范围互斥，建议状态与实际结论一致；无静默删减、建议升级或未经确认的范围扩张。
- 从业务使用者与验收者角度走读主链路和失败去向，关键术语可理解，页面入口、状态、权限、数据、配置消费和适用的性能安全兼容边界完整。
- 按R项走读依据、业务行为、页面/数据边界及单项验收，核对跨R项流程、共用页面与共用目标均有明确引用；业务规则、单项标准与集成标准各有维护位置，未把需求标准写成执行结果。
- 本次纳入项均能追溯到可执行验收；同一概念无多种口径，推断未冒充事实，内部实现未被包装成业务要求。
- 原型引用真实且状态明确，内容足以支持后续计划；依据语义与证据复核，不以固定标题、文件名或字段匹配替代内容验收。
