# 操作场景、默认权限与通配规范

本文定义命令选择、场景模式、例外规则与匹配语义。实际默认配置只在[默认JSON](../assets/command-policy.json)，项目生效配置在`OPS_ROOT/command-policy.json`；授权与执行顺序见[主流程](../SKILL.md)，留痕见[记录契约](records.md)。首次接入、宿主或执行通道变更及命令确认衔接时读取[宿主接入](host-integration.md)，本文不维护注册或答复核验流程。

## 先选场景和默认行为

先定位服务器、身份、管理入口及操作目的，再选原生、直接命令。查看状态不用重启试探，核对配置不用重新部署试探；普通过滤、排序、格式和有限采样由执行者自行选择，不为参数拼写反复申请权限。

下表适用于策略有效、目标已覆盖、采用来源已核实且命令通过语法与包装检查的情况；异常先按[判定结果与下一动作](#判定结果与下一动作)处理。每个场景只选一种模式，根据该场景实际常用操作中需授权与免授权的分布，以及例外维护成本确定；不统一强制默认询问，也不按任务复杂度分流。

| 模式 | 适用情况 | 唯一例外表 | 未命中例外时 |
| --- | --- | --- | --- |
| 默认放行：`default: allow` | 常用操作以免授权为主，需授权操作容易集中列出 | 只配置`ask`，不配置`allow`，即使空数组也不允许 | 直接allow |
| 默认询问：`default: ask` | 常用操作多需授权，只有部分操作可直接执行 | 只配置`allow`，不配置`ask`，即使空数组也不允许 | 返回ask；人工确认统一按主流程处理 |

禁止行为统一维护在顶层`deny`，对所有场景生效。禁止项是共同红线，不是第三张与两类例外平行维护的常规权限表；不能为同一场景同时列放行表、询问表，再推测谁更具体。

默认配置中，Docker采用默认放行，仅列变更、执行、传输发布、切换管理端点及受限内容等询问例外；不枚举Docker查询白名单。其他命令采用默认询问，仅列免询问查询，不再重复列一大批本来就会询问的命令。未覆盖场景返回ask；已命中默认放行场景的未知子命令也继承allow，不能再用“未识别”暗中改回白名单模式。更新工具或改变使用范围时复核询问例外。

## 操作类别与规则取舍

- **通常免询问**：身份/版本、列表/状态/元信息、资源快照及普通诊断查询。在默认放行场景不写规则；在默认询问场景只把实际要放行的查询写入allow。
- **通常需询问**：启停/部署/更新/删除，文件/权限/账号/网络变更，受限内容或业务数据访问，导入导出/对外发布，以及超出任务边界的持续或高开销采集。在默认放行场景写ask；在默认询问场景不再列同义ask规则。磁盘格式化、覆盖写有合法用途，属于高风险询问，不按工具名一刀切禁止。
- **建议禁止**：泄露秘密、绕过身份/主机核验、越过明确禁止范围、删除系统根目录等不允许的行为或对象。只写到共同deny，普通任务批准不能覆盖；改变禁止边界先明确修改策略。

allow只决定动作是否免额外询问，不代表任意目标、秘密输出或无界采集。执行前选定对象、字段、行数和时间窗，统计默认快照、事件查询默认有截止时间；普通诊断自行裁剪/脱敏，不因潜在敏感字段就整体增加审批。不向工具回执、对话或Git输出私钥、密码、Token、进程环境或含秘密的整份配置。数值有效性、路径归属、秘密和业务范围由执行者核对，通配器不判断这些语义。

复合部署/构建入口可以整体作为询问例外，不再从该例外中逐条加白名单豁免。确需单独管理其中的查询时，为该入口建立独立场景并重新选模式，而非在原场景恢复两张相反的常规权限表。

## 配置契约

顶层仅有`version`、`targets`、`approval_ref`、`deny`和`scenarios`。版本为正整数；targets是精确的`{server_id,user}`对；approval_ref指向真实采用/批准来源，未采用时为null，不能伪造批准。场景只含`name`、`prefix`、`default`以及与默认行为相反的一张例外表。

下列是场景对象的模式写法示意，完整配置以默认JSON为准。

默认放行场景只列询问例外：

```json
{
  "name": "docker",
  "prefix": "docker --host unix:///var/run/docker.sock",
  "default": "allow",
  "ask": [
    "{run,exec,rm} **",
    "service {create,update,rm} **"
  ]
}
```

默认询问场景只列放行例外：

```json
{
  "name": "general",
  "prefix": "",
  "default": "ask",
  "allow": [
    "id **",
    "df **"
  ]
}
```

prefix是实际命令的字面量参数前缀，不支持通配；固定程序、已核实管理入口或明确子入口。空prefix表示兜底场景。Docker命令和prefix先按下节做同样的参数规范化，再选参数前缀最长的唯一场景；不合并其他场景的例外，不依赖数组顺序。例外只匹配去掉prefix后的参数，因此Docker规则直接写`service update **`，不反复抄完整socket前缀。

## 通配写法

| 写法 | 含义与用途 |
| --- | --- |
| `*`、`?`、`[abc]` | 在一个参数内匹配，不会吞掉额外参数；例如`systemctl restart *.service`不含其他选项 |
| 独立`**` | 匹配零个或多个完整参数；例如默认放行Docker的询问例外`service update **`覆盖该变更的参数组合 |
| 整个参数的`{a,b}` | 新场景格式的单参数备选，可包含参数内glob；例如`service {create,update,rm} **`合并同类风险动词，`** {--context,--context=*} **`覆盖分开与等号形式 |
| `prefix` | 精确字面量前缀用于选场景；场景边界固定后，例外内不再重复它 |

命令及模式按shell引号分词，引号本身不参与匹配。备选组不允许嵌套、空项或将`**`放入组内；只占一个参数，不是shell执行或多段命令。Go模板的双花括号保持字面量含义。实际执行中的未引用通配、花括号展开、变量、命令替换、控制符、重定向及组合命令不会直接allow。

这不是文件系统路径glob：`*`能匹配同一参数里的`/`，不能阻止`..`、软链接或跨目录逃逸。路径限制须核对实际规范路径与任务边界，不能把字符串命中当作隔离。实际执行使用具体对象，不原样执行规则里的`*.service`。

程序路径只在限制匹配时作保守处理：deny及整命令ask规则的首参数不含`/`时，按程序名同时约束裸命令、绝对路径和相对路径，例如`dd **`也限制`/bin/dd …`、`./dd …`；含路径的规则仍约束其原路径。只处理程序位置，不改写操作数或读取文件系统/符号链接。allow和场景prefix保留字面路径，`id`不会自动信任`/tmp/id`，需要放行已核实路径时显式配置。任意程序改名、链接及实际行为仍须执行者审阅，文本匹配不是系统级隔离。

例外动词放在实际子命令位置，避免`** rm **`把查询对象名`rm`误认成删除。参数例外需覆盖短选项、长选项及`--flag=value`；备选组用于合并相同位置的变体，不用大量重复整条命令。默认询问场景的allow须能独立表达安全范围，不能再配ask补洞；表达不了就收窄该allow，或把整个子入口另设场景后选择默认放行模式。

### Docker参数规范化

Docker只在根命令和已识别管理命令的子命令之前解析全局参数，按参数元数识别长选项、等号形式、短选项及短选项连写。匹配时统一同义全局参数写法，并分别处理：

- 移除debug/log-level/help/version等显示参数。
- 保留host/context/TLS等会改变目标或安全边界的参数，供例外匹配。
- 操作数、inspect对象名和exec负载保持原样，不用`**`猜测动词位置。

未知或不完整的前置全局参数返回`unsupported-docker-options`，不能落入默认allow。全局参数语法统一在原判定器处理，权限仍由项目策略决定。

### Docker共同deny匹配

Docker共同deny先保留原始参数匹配，再将规则和命令交给同一个解析函数转为规范形式配对匹配；即使命令已经是长选项形式，也必须复核短选项或等号形式写成的规则。回执pattern始终保留原规则原文。

规范形式的处理保持以下语义：

- 布尔开关的隐含true及1/0、t/f等写法统一，true与false保持区分。
- 规则中的显示开关同样被忽略，不用它们收窄底层禁止操作。
- 参数值的glob和单参数备选继续有效，操作数不作全局参数转换。

Docker规则须有可确定的程序名及全局参数/命令前缀，仍支持`docker **`等整类禁止。歧义前缀、不支持的全局语法，或备选展开超过256个变体时返回`invalid-policy`，不得忽略该deny后继续默认放行。非Docker规则及旧格式除上述程序路径限制和包装检查外保持原匹配语义。

### 变更入口别名

同一变更入口的官方别名必须同判：例如`rm/remove`、`stack deploy/up`、`stack rm/down`。将别名并入原风险动词组，不为每个别名复制一份完整规则；测试同时覆盖真实变更、全局参数变体和同名查询对象。

## 判定顺序与执行边界

[check_command.py](../scripts/check_command.py)只分类命令文本，不连接或执行、不核验批准真伪或秘密，也不提供系统级隔离。调用方按以下顺序消费结果：

1. 校验策略并核对精确目标/账号；不满足时停止依赖操作。
2. 对命令分词并匹配原始共同deny，再检查shell展开；语法无法解析时不能进入匹配。
3. 规范化Docker参数，复核规范形式的共同deny，再检查包装命令。
4. 选择最长前缀的唯一场景，匹配其反向例外；未命中用场景默认行为，无场景返回ask。拟allow但没有采用来源时返回`unapproved-policy`。

### 判定结果与下一动作

先读取`decision`和`reason`，不能仅凭退出码或ask决定发起命令确认。下表维护分类结果的处理入口；任务审批范围由[主流程的审批判定](../SKILL.md#审批判定)维护，Hook如何继续、确认或停止见[宿主接入](host-integration.md)。

| 结果或原因 | 下一动作 |
| --- | --- |
| `deny / deny-pattern` | 停止；普通任务批准不能覆盖共同禁止项 |
| `ask / invalid-policy` | 恢复有效策略，重新核对deny后再判定；不得用单次命令确认绕过 |
| `ask / target-not-covered` | 核实目标、账号及策略覆盖关系，再判定；不得把未登记目标视为已授权 |
| `ask / unapproved-policy` | 核实真实采用/批准来源，按既有授权维护策略；不能用本次命令答复伪造策略采用来源 |
| `ask / unsupported-shell`、`shell-expansion` | 展开并审阅完整动作，改为具体对象和可直接分类的单条命令后重新判定；不能可靠改写则停止并说明缺口 |
| `ask / unsupported-docker-options` | 核对实际参数及解析器支持范围，存在等效受支持写法时重新判定；否则停止，不忽略参数或改动目标来获得放行 |
| `ask / wrapped-command` | 按下方包装边界处理；当前Hook停止，不进入普通命令确认 |
| `ask / scenario-default`、`scenario-exception`、`scenario-not-covered` | 普通ask，进入主流程的当次命令确认 |
| 旧格式的`ask / ask-pattern`、`unmatched` | 普通ask，进入主流程的当次命令确认；不因此迁移策略 |
| `allow` | 按主流程核对任务范围及适用的变更方案批准后继续；不扩大对象、输出或采集范围 |
| 未识别的结果或原因 | 停止并核对判定器与适配器版本，不能自行归入普通ask |

### 传输与包装边界

SSH由[宿主接入](host-integration.md#覆盖与失败边界)核对传输和目标后，将远端内层命令交给判定器；连接授权按主流程处理。直接把SSH包装传给判定器仍会得到`wrapped-command`。

sudo、脚本、解释器、`builtin`以及Docker根入口/`container`入口的`exec`、`run`属于包装。两个策略格式均在放行规则之前返回`wrapped-command`，即使策略例外列出了这些动词也不能改变该停止分支。Docker按实际动词位置识别，`inspect exec`等对象名不受影响。

执行者审阅真实内容和内层动作，内层deny即停止。内层分类仅用于审阅，不能解除外层停止：当前Hook没有接通包装负载审阅后的放行路径，审阅完成或取得普通命令答复后重试原包装仍会停止。能保持目标、身份、容器/主机命名空间及副作用等效时，可改用受支持的直接命令并重新判定；例如不能把容器内`id`替换成宿主`id`。无等效入口时报告当前通道不支持该动作，暂停依赖步骤，不关闭Hook或换通道绕过。

## 执行方式

优先复用已核实且当前通道支持的维护入口和直接命令；只为稳定复用或明确误操作防护编写脚本，不为留痕、包装SSH或统一输出搭建执行框架。采用前先按上述包装边界核对可执行性，审阅脚本不能替代受支持的执行路径。方案及命令生成时机由主流程维护，实际命令、入口版本与结果按记录契约保存。

实施、验证和回退分别核对，异常先查已完成动作及实际状态，不盲目整段重跑。自动重试或条件回退逻辑须先在可控环境验证对应分支；条件未知时停止依赖步骤，不在目标服务上首次试验自动恢复逻辑。

## 初始化、迁移与验证

首次采用默认基线按[工作空间初始化](workspace.md#初始化)处理。新增场景先判断哪类操作占多数，再选默认行为、只写反向例外，最后配置共同禁止项及测试；模式切换是权限变更，不能只换default而保留旧的相反例外表。

旧版顶层`default/allow/ask/deny`格式继续按原默认询问语义兼容，旧模式中的花括号不新增备选含义；新配置不再使用旧格式。已有项目不自动迁移，用户要求时才展示差异、取得覆盖相应放宽的批准、递增版本并整体切换，保留真实来源与有效限制。

配置验证覆盖两种模式：未命中例外时确实采用默认行为；命中时按反向例外决定；共同deny优先；规则与命令分别采用短/长/等号形式并加入显示参数时交叉同判；同一场景同时含allow/ask必须报错；重叠前缀只选一个；备选动词、参数变体、对象名rm/exec、未登记目标、草案及旧格式均有正反例。复用原判定器和测试，不另建平行权限系统。

```bash
python3 <技能目录>/scripts/check_command.py \
  --policy <项目策略.json> \
  --server-id <服务器ID> \
  --user <账号> \
  --command 'docker --host unix:///var/run/docker.sock service ls --filter name=portal'
```

输出decision/reason/pattern/policy_version，已选场景的新格式另给scenario/mode；退出码allow=0、ask=2、deny=3。退出码2包含普通待确认和停止分支，须按上述“判定结果与下一动作”处理；分类结果本身不签发许可。
