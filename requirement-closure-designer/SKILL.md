# 需求闭环设计器

## 核心定位

本技能不是独立重做一遍需求分析，而是 `requirement-doc-generator` 的“闭环模式”包装层。

执行本技能时，先完整读取 `~/.claude/skills/requirement-doc-generator/SKILL.md`，继承其中与以下事项相关的分析规则：

- 结合项目现状调研需求
- 以“资深业务专家 + 顶级系统业务需求分析师”的视角补全需求
- 区分阻塞确认、非阻塞确认和推断决策
- 明确标注未知信息，不把猜测写成事实
- 优先沿用项目已有模式，不轻易引入新抽象

项目材料按内容语义、用户明确指向和可证明的文档关系选取，不绑定固定文件名，也不因为文件位于同一目录就自动视为当前需求的输入。

但要强制切换到“需求闭环设计”阶段，而不是正式需求文档阶段。

继承范围限于上述分析规则，不继承正式 PRD 的章节、编号、原型及生成审批流程；闭环阶段的输出、保存和产物规则由本技能自身维护。

## 本技能相对 requirement-doc-generator 的收窄规则

- 默认不要在首次响应时创建、覆盖或更新任何文档文件；先在对话中输出闭环分析、阻塞确认项和非阻塞确认项。
- 当前不要生成 `requirement.md`。
- 当前不要进入正式需求文档写作，不要主动展开文档章节、输出目录、需求编号、验收标准、性能与安全要求、兼容性要求等终态文档内容。
- 当前不要确定或创建正式需求文档目录，不要分配 `R1`、`R2` 等需求编号，不要把闭环分析整理成可直接落库的 `requirement.md` 终稿。
- 目标是补齐“这个需求在系统里怎么真正跑通”，不是把用户原话换一种方式复述，也不是提前写成 PRD。
- 用户仅要求闭环分析时，只有接口、数据、上下游或配置机制影响闭环成立才展开相关内容，不为凑模板增加技术章节。用户同时要求技术方案等成果时，在首次输出中明确分区承载；保存时保留用户要求的全部成果，不因本技能默认范围而删减。
- 闭环分析部分只确定业务成立所必需的系统行为、边界和外部契约，不指定类、函数、表索引、内部事务编排等实现；用户另行要求的技术方案在对应部分承载，不能把实现选择升级为业务要求。
- 当用户明确确认闭环分析没有问题、确认闭环内容可落地，或要求保存、生成、更新闭环结果时，保存其指向的当前有效成果，并保留确认状态；闭环文档不是正式 `requirement.md`，不得顺带生成正式需求文档。
- 只有用户明确要求生成、保存或更新正式需求文档、PRD 或 `requirement.md` 时，才切换回 `requirement-doc-generator`。
- 用户仅确认闭环分析、认可方向、要求保存闭环文档或要求继续细化闭环时，不得自动进入正式需求文档生成。

## 输出与保存契约

先区分用户要求的操作，再选择流程：

- **首次生成**：按本技能的“首次输出的默认结构”结合需求确定结构并完整分析；用户明确要求转换为正式 PRD 时，才切换到需求文档技能。
- **保存已有成果**：用户要求“保存上述内容”“先存文档”时，以其指向的成果及后续修正为基线，执行下列保存规则及适用的路径规则；不重新分析、套用模板或自动转换为正式 PRD，也不额外生成原型、需求编号等产物。
- **修改或重构**：以当前有效文档为基线，在用户要求的范围内更新；只有用户要求精简、重排、拆分或转换时，才进行相应结构变换，未涉及的内容保持完整。

保存已有成果时：

1. 沿用已有章节顺序、层级和内容范围；仅有评审摘要时保存该摘要，不把它当作完整正文重新生成。多个候选成果无法根据上下文确定时，才询问保存对象。
2. 完整保留有效信息，包括功能细节、理由、例子、边界、表格、图示和引用，分别继承事实、已确认结论、建议、假设和待确认状态。保存授权不等于内容获批；存在未决问题也可按要求保存当前草案，不得标成已确认终稿。
3. 允许修正格式、措辞和指代，移除寒暄、执行预告等非成果话语；不得用摘要替代详细内容。用户明确要求逐字保存时，按原文保存。
4. 后续有效补充融入对应章节，保留一份连贯正文；不通过附加聊天全文、旧稿或重复附录代替整合，不擅自拆成多份文件。发现实质冲突时说明并标注待确认，不静默取舍。
5. 写入前后对照保存基线逐项核对章节、信息覆盖和结论状态，并检查新增内容、重复和冲突。字数增加、标题齐全或复制旧稿均不能证明内容完整；复核无需另建过程文档。

## 闭环文档生成规则

用户确认闭环或要求保存时，遵守本技能的“输出与保存契约”，并应用以下闭环专属规则：

1. 写入时机。
   - 阻塞确认项未解决时，不得将内容标为最终确认版本；用户要求“先保存”即可保存当前草案并保留未决状态，不要求其重复声明“按假设保存”。
   - 用户已经确认闭环无问题且输出路径可确定时，直接保存，不再追加一次确认。
   - 保存后只报告文件路径、是否覆盖或新建、仍需用户关注的遗留项；不要继续生成正式 `requirement.md`。

2. 输出目录。
   - 输出目录遵循全局协作规则 `~/ai-agent-config/config/force/collaboration-rule.md` 的“建文档目录时”。
   - 生成前检查目标 `requirement-closure.md` 是否已存在；若已存在且用户没有明确要求更新该文件，不要覆盖。能够判断不是同一功能时，按全局目录规则选择更精确的需求目录；能够判断是同一功能但是否更新不明确时，先确认。

3. 文件命名。
   - 默认文件名固定为 `requirement-closure.md`。
   - 只有用户明确指定其他文件名时，才使用用户指定文件名。
   - 不要把闭环文档命名为 `requirement.md`，不要在闭环文档阶段生成 `prototypes/`。

4. 产物边界。
   - 保存闭环成果不自动扩写为正式需求文档，不额外生成需求编号、正式验收标准、性能安全或兼容性专章及页面原型；用户已明确要求并纳入保存基线的内容仍完整保留。

## 闭环分析目标

输出结果必须能回答清楚：

- 谁来用
- 从哪里进入
- 如何一步步完成操作
- 系统如何反馈
- 结果如何保存、如何生效、如何回退
- 失败时如何处理
- 最后如何判断闭环成立
- 哪些内容必须实现、哪些只是建议、哪些明确不在本次范围，以及三者之间是否互不冲突

重点是补齐完整功能闭环，而不是只复述核心诉求。

分析不确定项前，先核实现有项目材料能够回答的客观事实，不能把可自行查证的问题转交用户决策；需要用户确认的应是会改变业务目标、范围、流程、状态、权限或验收结果的选择，或因依据确实不可访问而无法继续判断的关键事实。

## 页面闭环规则

涉及页面时，闭环阶段必须先确定页面入口、页面职责、关键操作链路、状态流转、数据变化、权限边界和异常反馈；不要求在此阶段展开完整页面布局和全部交互细节，但不能把影响业务闭环的页面信息留到正式需求文档阶段再补。

具体约束如下：

- 如果页面、弹窗、抽屉、配置入口会影响业务闭环成立，必须在本阶段讨论清楚。
- 本阶段必须明确：有哪些页面或入口、谁从哪里进入、每个页面承担什么职责、页面之间如何衔接、联动和回流、有哪些关键操作链路、会触发哪些状态变化、数据变化或数据流转、权限边界以及异常、空状态和失败反馈。
- 本阶段不要求展开成正式页面设计稿，不要过早细化布局、字段顺序、按钮位置、文案、表格列宽、组件样式、交互微文案和视觉稿。

## 首次输出的默认结构

以下模板用于组织首次完整闭环分析，不适用于保存时重新编排已有成果。首次输出前根据需求规模和用户要求确定实际结构：简单需求可合并相近章节，无关章节可省略，复合请求可增加对应部分；仍须回答“闭环分析目标”中的适用问题，覆盖页面闭环、范围和未决事项。用户指定格式时优先采用。确定后按该结构完整输出，后续保存直接沿用。

```markdown
# 需求闭环分析

## 1. 初步需求理解

## 2. 业务目标

## 3. 用户角色、权限与使用场景

## 4. 完整业务闭环
- 主链路
- 关键支链路
- 状态流转
- 失败处理与回退方式

## 5. 完整功能点清单
对每个功能点说明：
- 功能目标
- 对应页面或入口
- 关键操作
- 系统反馈
- 状态变化
- 权限或配置要求
- 异常处理

## 6. 页面闭环草案
仅输出对闭环成立有直接影响的页面信息，包括：
- 页面/弹窗/抽屉/配置入口
- 页面职责
- 入口与跳转关系
- 页面之间的衔接、联动与回流关系
- 关键操作链路
- 状态变化
- 数据变化或数据流转
- 权限边界
- 异常、空状态与失败反馈

## 7. 阻塞确认项

## 8. 非阻塞确认项

## 9. 范围划分
- 必须实现
- 建议实现（每项标注处理状态）
- 暂不实现

建议实现的处理状态只使用：`本次纳入`、`后续建议`、`已实现`、`待确认`、`不纳入`。闭环阶段只能基于当前事实标注，不能把未落地事项写成已实现。

必须实现、建议实现和暂不实现必须互斥；同一功能点不得换一种表述后重复归入不同范围。

## 10. 推断依据与推断决策

## 11. 后续建议
说明当前是否已经具备保存闭环文档的条件，以及是否已经具备进入正式 `requirement.md` 生成的条件。
```

## 质量要求

- 优先补全业务闭环和系统落地路径，不要写成泛泛的 PRD 套话。
- 不要为了追求结构完整，提前固化未确认内容。
- 如果关键前提不明确，先列为阻塞确认项，不要强行编造。
- “完整功能点清单”和“页面闭环草案”不要重复抄写同一批内容；前者按功能链路组织，后者只补页面职责、页面衔接和页面层面的闭环信息。
- “建议实现”必须带处理状态，用于后续判断是否纳入、已做或暂不处理；状态缺失视为闭环信息不完整。
- 项目事实、用户确认结论、推断决策和未决问题必须能够被区分；没有依据的推断不得写成事实，阻塞确认项未解决时不得伪装成闭环结论。
- 生成时按用户诉求复核闭环是否成立；保存时按本技能的“输出与保存契约”复核指定成果是否完整落盘。章节可适配不等于内容可缺失，固定模板不能替代语义判断。
